# Google Tasks：既存端末の更新後に同期できない問題

2026年11月12日、日本時間。同じ作業コピーの `main`、基点 `e5652ce`。この作業ではcommit・pushしない。

## 実機で特定した原因

iPhoneの保存状態は、Tasksの接続が有効である一方、`last_error_code=err_internal_sqlite_error` だった。個人DBはschema 29、`quick_check=ok`。作成予約の `private_google_task_create_intents` は存在したが、応答記録の `private_google_task_create_results` が存在せず、実際のSELECTで `no such table` を再現した。

作成予約の初期化はschema 24への移行にしかなく、その後同じ初期化関数へ応答記録テーブルが追加されていた。すでにschema 29へ更新済みの端末では関数が再実行されず、Tasksの復旧照合が最初の取得前に失敗していた。新規DBでのみ同期を検査すると発見できない更新処理の不具合。

前回の[Google再接続の実機検査](./google-sync-reconnect-2026-11-12.md)で実測した対象はCalendarだった。Tasksの模擬テストの成功を、実機のTasksが復旧した根拠として使うことはできなかった。

## 修正

- schema 30への移行で、予約・応答記録の初期化を1度だけ実行する。`CREATE TABLE IF NOT EXISTS` を既存の移行トランザクション内で実行し、保存済みの予約・対応表・家事・履歴を削除しない。
- 移行の途中失敗はDDLとバージョンをまとめてロールバックし、次回に再試行する。schema 30の通常起動では新たな書き込みトランザクションを増やさない。
- 端末のSQLiteエラーをOAuth設定不備として案内しない。未分類の接続失敗でも利用者に開発用設定の変更を求めない。

## 実施した検査

- 修正前に旧schema 29・応答テーブルなしの状態で失敗することを確認。修正後は、テーブルなし／既存応答あり／途中失敗からの再試行の3ケースが通過。未確定の作成予約を消して重複POSTを許すこともない。
- 実機から採取したDBの別コピーで実際の移行コードを実行。既存53テーブル・4,923行は全内容が不変で、応答記録を読めるようになり、schema 30・`quick_check=ok` を確認。これは実機上のGoogleとの同期成功とは区別する。
- 更新・設定表示の回帰検査34件、Tasksの照合・作成結果復旧・取消し・取得キャッシュ・関連DB移行・Nativeウィジェット検査173件が通過。重複を含むため合算しない。
- lint・型検査は通過。679の機能契約と118のCloud回帰検査の登録を確認。今回、全プロジェクトのテストやCloudエミュレーター全件を再実行したとは扱わない。

## 実機で追加発見した復旧の不具合

最初のRelease導入後、実機でもschema 30・応答テーブルあり・`quick_check=ok` を確認した。ただし実際のTasks同期は `task_create_result_pending` で終わった。これは通信障害の実測ではなく、作成結果の照合を完了できない状態だった。

保存済みデータを調べると、対象の作成記録にはGoogleが返したタスクIDがある一方、その家事回の対応表がなく、取得済みデータには同じIDの削除済みタスクが残っていた。再送の防止記録が永続的に作成を妨げる条件。

- 予約が取れない場合だけ記録済みのIDを読み、GoogleへそのIDを再確認する。通常の作成・同期に追加のGETを増やさない。
- 削除済み応答またはNotFoundが確定した場合にだけ、そのIDに一致する予約を解除して未完了の家事を修復する。すでに完了した家事の履歴はGoogleへ再作成しない。
- 生存するタスクが見つかった場合は同じIDの対応表を復旧する。次の通常照合でGoogle側の完了を先に取り込むため、復旧中に未完了へ上書きしない。
- 通信失敗、別IDの応答、IDがまだ不明な予約では再作成を許可しない。「確認待ち」を一律に通信エラーとして案内しない。

この追加修正は、削除済み／NotFound、個人の完了有無、古い取得結果、生存タスクの完了取り込み、通信失敗・別IDの応答を含む回帰検査で確認した。関連247件が通過し、その後の取得位置メタデータの型修正は該当80件を再実行して通過した。件数は重複を含むため合算しない。
