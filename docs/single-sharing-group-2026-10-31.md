# 同時所属を一つに統一する変更

2026-10-31のユーザー指定を優先し、複数グループへの同時所属を廃止する。共有データの保存先は一つとし、個人の家事・予定は同じ4タブに重ねて表示する。個人の設定・履歴・Google情報を共有する変更ではない。

## 削除した処理

- グループ選択UIと、個人モードへ戻る操作。
- Contextのグループ配列と任意の表示先へ切り替えるAPI。
- 前景で複数のグループを購読するループ。
- 背景workerの複数グループ巡回、順番入れ替え、巡回位置の保存。
- 通知を押した際のグループ切り替え。現在の所属先と一致する通知だけを同じホームへ案内する。
- Cloudの所属一覧ページング。所属確認は固定された1件を読み取る。

## 作成・参加・退出

SQLiteの`sharing_current_workspace`に1ユーザー1枠の所属を保持する。作成待ち・参加申請待ちもその枠を使い、別の作成・参加を拒否する。退出または申請取消後に、次のグループへ参加できる。所有者に他メンバーがいる場合の所有権移譲は維持する。

Firestoreの`sharingUsers/{uid}/memberships/current`も同じく1枠とする。グループ作成・参加申請は所属枠と同じatomic writeで確定し、別端末の同時操作でも両方を確定させない。別グループの所有者が既存の所属を書き換える操作や、所属確認を省いて名簿へ追加する操作も拒否する。

競合でクラウド作成を拒否された端末は、他の所属先が確定していることを確認してからローカルの作成枠を解放する。未送信の編集・イベントは消さない。通信障害だけで所属を解除しない。所属確認の追加処理も元のworkerの時間予算を消費し、終了後に新しい同期枠を与えない。

## 既存データ

以前表示していたグループを、既存の記録と鍵のまま単一の所属先へ結び付ける。既存のグループDB、履歴、未送信変更、過去の検査用の参照は保持する。退出後に過去の別グループが自動選択されることはない。旧アプリ向けの複数所属indexや旧Rulesへ書き込む互換処理は追加しない。

## 検証の扱い

複数グループの切り替え・公平な巡回を必須としていたfeature contractは、今回の指定に合わせて単一所属の回帰検査へ置き換えた。認証・暗号・権限・再送・保存・個人データ分離の検査は維持する。復旧OFFでも通常同期が使える検査は、現在の単一所属Rulesに対して継続する。旧Rulesのfixtureと過去の監査記録は履歴資料として保持する。

自動検査、Cloud結合検査、端末での表示確認、Rulesの配備は別の実施記録として扱う。自動検査の成功だけで実端末確認や本番配備を完了としない。

### コード・隔離環境での結果

- `npm test`: 2,473件成功。
- Firestore/Auth Emulatorによる`npm run test:sharing-cloud`: 105件成功。
- TypeScript・Expo lint・差分の空白検査: 成功。
- 同時作成、同時参加、参加待ちの二重所属、所有者による横取り、退出後の履歴保持、作成拒否時の枠解放、workerの時間予算を回帰検査した。

実機・シミュレーターの表示確認と本番Rules配備は、上記の自動検査に含めない。

その後の個人・共有UI統一、連続した設定文書、読み込み重複の除去、および最終2,485件の検査結果は[UI修正の記録](ui-unification-2026-10-31.md)にまとめる。

### Rules配備

既存アプリ設定のFirebaseプロジェクトをCLIで照合し、`firestore:rules`だけを配備した。データ・index・ユーザー・鍵の削除は行っていない。配備したRulesのSHA-256は`3cb4493e68f1fae256f5619b2dfde087c06d9c485cef5cdf971850b69f39ed66`。単一所属のindexへ切り替えるため、新しい作成・参加には更新後のクライアントを使う。以前参加済みのグループは記録を保持したまま結び付ける。
