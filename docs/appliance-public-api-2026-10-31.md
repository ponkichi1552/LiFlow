# 家電AI：アップロード説明書と公開受付の保護

## 現状と公開の停止条件

家電AIの実行だけGoogle／AppleのFirebase認証を必須にした。匿名認証には枠を付与しない。通常の個人Planner、保存済み家電の説明、既存の共有履歴はログイン不要の個人利用を維持する。AI画面からのログインはグループの作成・参加を行わない。

**正規アプリ・端末継続性を検証する本番アダプターは未接続。公開APIは現在、起動時に停止する。** Firebaseのログイン成功、端末が送ったID、App CheckのappIdだけを根拠に「同じ物理端末」と認定しない。`createPublicApiAccess`に注入する端末検証器は、改ざん・再送を拒否したネイティブ証明から端末の仮名IDとインストールIDを返し、再インストール判定を確認済みにできる必要がある。未設定・不明なら503/403で解析しない。確認を省略する環境変数や公開用のdebug token経路は用意していない。

iOSのApp Attestだけでは再インストール前後の端末を識別できない。DeviceCheck等の継続性の仕組み、Apple側の鍵と資格が別途必要。AndroidもPlay Integrity／Device Recall等の構成と検証が必要であり、Device Recallは利用資格・承認と機能上の制約がある。これらの設定・本番検証が未完のため、今回の自動テストは正規端末検証そのものの成功を証明しない。Apple Developer Programやストアの契約・課金・資格情報発行は今回行っていない。

## 確定した回数ルール

- アカウントと検証済み端末の両方に月5回。使用数の大きい方（残回数の少ない方）へ両方を同期する。端末の自己申告値を使わない。
- 毎月1日09:00 JST（UTCの毎月1日00:00）に新しい月の枠へ移る。端末時計を使わない。
- 月に最初に紐づいたアカウントを固定する。解析0回でも端末確認済みの紐付けを保存し、通常のアカウント切替では置き換えない。再インストール後も元のアカウントを確認できれば未使用の5回を利用できる。端末側に別の利用があれば、その少ない残回数を適用する。Google／Appleログインだけで端末確認が未完の場合は、紐付け済みと扱わない。
- 同じ検証済み端末で新しいインストールIDを検出したら、その月は最初のアカウントだけ解析可能。別アカウントは翌月から利用可能。旧インストールIDを再送しても当月の制限を解除しない。
- 拒否されたアカウントの要求でも、より厳しい使用数と再インストール制限の記録はトランザクションを確定して残す。
- 再解析も1回。受付時は月の枠を仮確保する。サーバーがOpenAI側のHTTPエラー・通信失敗・空白だけを含む空の応答等で解析結果を取得できなかったと確認し、受付記録へ確定した場合だけ月の枠を戻す。拒否回答・返却済みの不正な解析結果・端末だけの通信切断や中止は返却条件に含めない。アプリの申告では返却しない。記録のない中断は成功にも返却にも読み替えない。
- 明示的な受付IDの再送は、保存されている同じjobへ戻す。同じ利用者の実行中・保持期間内の検証済み結果は通常実行時に再利用する。失敗した結果の新しい再試行は可能。
- OpenAIの無応答で月の枠を戻した場合も、全体の受付試行数は戻さない。サービス全体1日20回、毎日09:00 JST更新。全体最大同時3件、同一アカウントまたは同一端末の同時実行は1件。
- 1解析は最大10分、AI呼出1回、出力16,384トークンまで。自動の有料リトライをしない。回数・トークンの上限は通貨建ての請求上限そのものではない。

## 説明書の送信と保存

通常の登録・再解析は、利用者が選んだPDFだけを解析する。`api:dev`もアップロード方式とする。過去の製品検索／公式URL解決コードは既存データ・検査用に残るが、通常のAPI起動経路では呼ばない。公開HTTPサーバーで旧方式を選ぶことも拒否する。

PDFは6MiB・100ページまで。送信確認を必要とし、任意URLやファイルパス、自己申告のhashを入力として認めない。サーバーが実際のバイト列からSHA-256を計算する。PDF構造の検査は環境変数を渡さない隔離workerで行い、5秒・メモリ上限・最大同時2件を設ける。PDFのJavaScript・XFA・外部リンク取得は使わない。同じhashの構造検査は原本を保存せず短期間再利用する。

OpenAIへはbase64の`input_file`を渡す。Web検索、外部ツール、`file_url`の取得は許可しない。PDF内の命令はデータとして扱い、長い引用や説明書全体の再現を避ける指示を入れる。これだけで著作権上の許諾を保証するものではなく、利用者が解析に利用できる資料を選ぶ。

解析結果の`manualSource.kind=user_upload`と`liflow-manual://sha256/<hash>`は、選択したPDFを識別する内部参照。メーカー公式URLやメーカー承認として表示しない。ページ・節名を残し、リンクとして外へ開かない。利用者の2026-11-01の指定により、PDFの原本を端末の個人SQLiteにも保持する。参加中の共有グループには、署名付きの暗号化イベントとして分割保存し、受信端末にも同じPDFと確認済み解析結果を保持する。AI APIのFirestore jobには原本を保存しない。ピッカーが作った一時コピーだけをキャッシュから削除し、Files等にある利用者の原本とアプリ内の保持用コピーは削除しない。AI提供元側の取り扱いは提供元のデータ方針に従い、`store:false`を即時・完全消去の保証と解釈しない。

既存の公式資料URLを持つ保存済み説明、ユーザーの周期・手順・完了履歴は保持する。新しい形式は共有契約`liflow-shared-2-draft-39`で扱う。draft38のグループは署名付きの38のまま、従来の予定・家電を読み書きできる。PDF由来の新しい共有解析は、所有者が全メンバーのアプリ更新を確認し、共有管理画面で互換更新した後だけ受け入れる。更新はメンバーを変えず、将来鍵を回転し、元の署名付き履歴をSnapshotに保持する。古い版への巻戻しは拒否する。

## 個人・共有の家電をまとめる（2026-11-01）

家電追加の個人／共有の選択は除いた。グループ参加中は一度の解析結果を共通家電として保存し、個人ライブラリにも製品情報・説明・PDFを残す。共有時の確認・保存操作は維持し、二度目の保存先選択や二度目の有料解析を挟まない。個人側で解析済みの同じ結果も、再解析せず共有保存する。既存のメーカー・型番が一致する家電は一覧で重ねて表示しない。固有の個人家電は引き続き開ける。

端末スキーマ21にPDFと共有コピーの対応表を追加した。家電の保持では個人の家事定義・周期・有効状態・担当・完了履歴をコピーも上書きもしない。個人で付けた家電名を保持し、グループ退出・共有側の削除でも既に保持した個人コピーを消さない。家電一覧だけを更新する経路を使い、予定全体を再計算しない。

共有契約`liflow-shared-2-draft-42`では、PDFを最大96KiBのバイト列ずつ分割し、各片と全体のSHA-256を検証する。暗号文は通常のOutbox・署名・受付記録・Snapshotを通す。PDFの不足、改ざん、異なるアカウント、別グループを拒否する。再送は同じ内容を再利用し、同じ家電を重複作成しない。従来のdraft-41の一般予定も継続して受信できる。新しいPDF付き解析の前に共有版の対応を確認し、未対応なら有料APIを呼ぶ前に止める。

以前の版で原本を保存していなかった家電から、失われたPDFを復元することはできない。保存済み説明・履歴はそのまま使える。後から同じPDFを保持できた場合は、製品情報を変更しなくても原本の保存を補完する。新規端末は追加イベントがなくても検証済みSnapshotからPDFを復元する。

### 保存・共有の追加検査

検査用に生成した架空PDFを使い、利用者の端末内ファイルや有料AIの実APIを使わずに確認した。端末でPDFを選ぶ操作と、選んだPDFを別の共有メンバーの端末へ転送する処理は別の段階である。「後から届く」は後者の受信順序・通信切断・Snapshot復元を指す。

最大6MiB／64分割、途中欠落・改ざん・不正base64・別のdigest、逆順・重複受信、保存途中の失敗、アカウント変更・別グループ、個人の名前・家事・設定・履歴の保持、共有からの削除後の保持、遅れて受信したPDFの補完、新しい端末のSnapshotだけからの復元を自動検査した。元の不具合は修正前に失敗する回帰として再現し、修正後に8件成功した。

Auth／Firestore Emulator上の106件の結合検査も成功した。実際のRules・署名・暗号化・不変な受付記録を使い、PDFが暗号文だけで保管されること、未認証・別グループからの取得拒否、送信応答が失われた後の同一イベント再送と復元を確認した。実サービスに大量の要求を送る検査ではない。

## サーバーの境界

Firebase Admin SDKの`verifyIdToken(token,true)`で署名・プロジェクト・期限・失効・無効化を検査し、Google／Appleだけを許可する。さらに正規端末検証を必須にする。認証前に有料処理を始めない。他人のjob IDは不在と同じ404。旧同期型`/analyze`からの迂回は不可。

`POST /api/appliance-care/jobs`はBearer認証と`x-idempotency-key`、製品情報、`manual:{base64,rightsConfirmed:true}`を受け付ける。`GET /api/appliance-care/jobs/:id`は本人だけ、`GET /api/appliance-care/usage`は同期済みの本人の残回数だけを返す。`/health`は公開構成の秘密や設定状態を返さない。

Firestoreの`applianceApi/v1`配下で、月次のアカウント・端末使用数、日次全体使用数、job、再利用先、実行予約、消費／返却の判断と使用数の根拠を管理する。上限照合のMAXと受付時の加算を不変な参照として残し、後から返却が起きてもコピー済みの使用数を再計算できる。正常な別の受付まで無料にしたり、同じ障害で二重に枠を増やしたりしない。

全クライアントの直接read/writeをRulesで拒否する。AdminはRulesを迂回するためホストのIAMを別途保護する。アカウント／端末枠とjob作成は1トランザクションで確定し、その後だけAIを始める。job・再利用先は7日、使用数と消費／返却の根拠は対象期間終了後90日保持。結果を削除した後も返却の証拠を失わない。起動時・1時間ごとに最大490文書ずつ期限切れを削除し、更新時刻の条件付き削除で新しい値の誤削除を防ぐ。共有家事や個人Plannerは削除対象に含めない。

OpenAI key・管理者資格情報はサーバーだけに置き、アプリへ同梱しない。APIホストはHTTPS、入口の要求制限、ログの秘匿、常時CPUを備えた構成を使う。受付後に常駐workerが動くため、要求完了後にCPUを停止するserverless構成へそのまま置かない。Dockerfileはビルド素材であり、公開や契約を自動で行うものではない。

## 検査と公開までに必要なこと

1. `npm ci`と`npm run api:install`を実行し、`npm run check`を通す。Admin SDK／PDF parserはサーバー専用packageへ隔離している。
2. Auth／Firestore Emulatorの`demo-liflow-sharing`でクラウド検査を行う。本番へ攻撃・負荷要求を送らない。
3. Apple／Googleの実サービスで正規端末・継続性検証を実装接続し、署名、challenge、期限、再送、アカウント・要求への結び付けを検証する。確認できない環境は停止を維持する。
4. 実端末で当月の最初のアカウント、アカウント切替、再インストール、翌月解除を確認する。現段階でこの実サービス検査は未完。
5. Firebaseプロジェクト、最小権限のADC／Workload Identity、サーバーSecret、HTTPSホストを設定する。匿名認証を有効化する必要はない。本番でAuth／Firestore Emulator設定を認めない。
6. アプリのHTTPS接続先を設定してビルドする。HTTP・別host・資格情報入りURLへ認証tokenを送らない。開発APIの認証なし待受はloopbackだけ。

この検査は開発工程内の検査であり、独立した第三者監査ではない。実施した範囲と未完の本番端末検証を分けて記録する。

## 後続の検査記録

- iOSシミュレーターのRelease版でPDFピッカーの起動・キャンセル、未確認時の解析停止、元の共有ホームへの復帰をXCTestで確認。個人DBの家事・家電・履歴等16テーブルは検査前後で一致した。有料の実APIは呼び出していない。
- Android 10実機へデータを保持してRelease版を上書きし、開発サーバーなしの起動（cold launch 2,150ms）、従来の共有ホーム、個人用PDF解析画面、Android標準PDFピッカーの起動・キャンセルと未確認時の解析停止を確認。実サービスの正規端末証明は未接続であり、実際の再インストール・有料解析のE2E完了とは扱わない。
- 同時再送の検査で、変わっていない使用数まで書き直す競合を発見・修正した。変更時だけ保存し、同じ受付の処理中要求をまとめる。複数サーバーでの受付はFirestoreのトランザクションで守り、有料workerは1つだけ開始する。
- 月の枠の返却は、複数アカウントへの照合後、遅れて発生した障害、重なった端末履歴、結果保持期間の終了、二重通知、月替わりと分けて検査する。ログイン0回ではなく、解析0回の端末確認済みアカウントも保護する。
- ローカルのlint・型検査は成功。iOS系統は2,444件と追加のアカウント画面2件、Android系統は2,446件を通過。Auth／Firestoreの全結合検査99件に加え、最終版の使用数根拠の永続化を含む公開API結合検査10件を再確認した。386機能契約・64必須Cloud検査の登録、SDK診断20項目も通過。Semgrepは対象21ファイル・110ルールで指摘0、ステージ済み差分のGitleaksは検出0。これらは検査対象と実施時点の結果であり、未接続の端末証明や独立監査の代わりにはならない。
- サーバー専用依存の監査結果は指摘0。rootは今回取得時点でhigh／critical 0、moderate 26・low 2。主にglob／minimatchと依存元への波及であり、28個の独立したアプリ攻撃経路という意味ではない。[globの告知](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4)と[minimatchの告知](https://github.com/advisories/GHSA-g3hv-75wg-m249)を照合した。SDK58を旧SDKへ強制変更する修正案や、互換性を無視した全階層のメジャー上書きは採用していない。ビルド・lint用のglob処理に、アップロードPDFや利用者のglob式を渡す経路は設けていない。
