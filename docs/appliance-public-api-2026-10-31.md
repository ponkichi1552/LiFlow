# 家電AI：アップロード説明書と公開受付の保護

## 2026-11-15：保存確認後の本文削除

端末がPDFと結果をSQLiteへ永続保存した後、本人認証付きの `POST /api/appliance-care/jobs/{jobId}/receipt` で受領を確認する。結果ハッシュ・受領トークン・所有者・有効期限が一致した場合に限り、APIの結果本文を削除する。確認応答を失って再送しても再解析・再課金しない。保存失敗時は削除しない。

未受領データの取得期限は24時間。期限後の実体は既存の清掃処理で削除する。受領確認は新たな有料解析ではなく、契約やネイティブ証明が失効した後でも本人確認を満たせば受け付ける。新規解析の認証・課金条件は維持する。これは配備前のコード変更であり、稼働済みAPIの削除を実行した記録ではない。[通信・サーバー保存の最小化](security/data-minimization-2026-11-15.md)に配備順と保持する最小情報を記載した。

## 現状と公開の停止条件

家電AIの実行だけGoogle／AppleのFirebase認証を必須にした。匿名認証には枠を付与しない。通常の個人Planner、保存済み家電の説明、既存の共有履歴はログイン不要の個人利用を維持する。AI画面からのログインはグループの作成・参加を行わない。

正規アプリと端末を検証する経路を組み込んだ。実際に使うには、Apple・Googleの有効な設定、配布署名、HTTPSのAPIと解析ワーカーが必要。購入確認のみ設定済みの場合は購入・復元が利用でき、端末証明が必要な解析経路は受付を停止する。料金の発生する操作はFirebaseの本人確認、契約確認、アカウントと受付IDに結び付いた端末証明、Firestoreの利用枠の照合を通る。端末から受け取ったIDやログイン結果だけで利用枠を発行する経路は設けない。

iOSはApp Attestでアプリと鍵を検証し、署名カウンターで使い回しを拒否する。Appleの開発チームで共有されるDeviceCheckの2ビットをLiFlow用に確保する。登録時にbit1をセットし、bit0の値を反転して更新月を記録する。照会と更新には別々のトークンを使い、両方をApp Attestの証明に結び付ける。鍵の参照は端末固有のKeychainに保存する。

Androidは、Play署名・ライセンス・端末の整合性に加え、Android Keystoreの署名とハードウェア鍵の証明書をサーバーで照合する。開発者アカウントで共有されるDevice RecallのbitFirstをLiFlow用に確保し、端末登録月を記録する。初回登録は、Device Recallの読み取りと更新が重ならないようサーバーで調整する。端末IDは端末内でハッシュ化し、サーバーでも専用鍵で仮名化する。

短い受付証明はメモリにだけ保持する。新規解析の証明は、認証済みのアカウントと対象の受付IDに結び付ける。ビルドの署名や端末の継続性を確認できない場合は、新規解析の受付を停止する。

## 確定した回数ルール

- アカウントと検証済み端末の両方に月5回。使用数の大きい方（残回数の少ない方）へ両方を同期する。端末の自己申告値を使わない。
- 毎月1日09:00 JST（UTCの毎月1日00:00）に新しい月の枠へ移る。端末時計を使わない。
- 解析が0回でも初回の端末確認を記録する。同じ鍵でアカウントを切り替えた場合は、端末または新しいアカウントの残り回数の少ない方を適用する。
- 再インストール後、OS側に同月の端末登録があり以前の端末鍵を確認できない場合は、新規解析を翌月1日09:00 JSTまで停止する。保存済み家電の閲覧は継続する。
- 拒否されたアカウントの要求でも、より厳しい使用数と再インストール制限の記録はトランザクションを確定して残す。
- 再解析も1回。受付時は月の枠を仮確保する。サーバーがOpenAI側のHTTPエラー・通信失敗・空白だけを含む空の応答等で解析結果を取得できなかったと確認し、受付記録へ確定した場合だけ月の枠を戻す。拒否回答・返却済みの不正な解析結果・端末だけの通信切断や中止は返却条件に含めない。アプリの申告では返却しない。記録のない中断は成功にも返却にも読み替えない。
- 明示的な受付IDの再送は、保存されている同じjobへ戻す。同じ利用者・同じ端末・同じインストールでは、実行中や保持期間内の検証済み結果を通常実行時に再利用する。失敗した結果の新しい再試行は可能。
- OpenAIの無応答で月の枠を戻した場合も、全体の受付試行数は戻さない。サービス全体1日20回、毎日09:00 JST更新。全体最大同時3件、同一アカウントまたは同一端末の同時実行は1件。
- 1解析は最大10分、AI呼出1回、出力16,384トークンまで。自動の有料リトライをしない。回数・トークンの上限は通貨建ての請求上限そのものではない。

## 説明書の送信と保存

通常の登録・再解析は、利用者が選んだPDFだけを解析する。`api:dev`もアップロード方式とする。過去の製品検索／公式URL解決コードは既存データ・検査用に残るが、通常のAPI起動経路では呼ばない。公開HTTPサーバーで旧方式を選ぶことも拒否する。

PDFは6MiB・100ページまで。送信確認を必要とし、任意URLやファイルパス、自己申告のhashを入力として認めない。サーバーが実際のバイト列からSHA-256を計算する。PDF構造の検査は環境変数を渡さない隔離workerで行い、5秒・メモリ上限・最大同時2件を設ける。PDFのJavaScript・XFA・外部リンク取得は使わない。同じhashの構造検査は原本を保存せず短期間再利用する。

OpenAIへはbase64の`input_file`を渡す。Web検索、外部ツール、`file_url`の取得は許可しない。PDF内の命令はデータとして扱い、長い引用や説明書全体の再現を避ける指示を入れる。これだけで著作権上の許諾を保証するものではなく、利用者が解析に利用できる資料を選ぶ。

解析結果の`manualSource.kind=user_upload`と`liflow-manual://sha256/<hash>`は、選択したPDFを識別する内部参照。メーカー公式URLやメーカー承認として表示しない。ページ・節名を残し、リンクとして外へ開かない。利用者の2026-11-01の指定により、PDFの原本を端末の個人SQLiteにも保持する。参加中の共有グループには、署名付きの暗号化イベントとして分割保存し、受信端末にも同じPDFと確認済み解析結果を保持する。2026-11-05の受付修正では、APIから独立したワーカーへ渡す一時入力だけを、Firestoreの私的キューへ専用のサーバー鍵で暗号化して保存する。平文PDFや鍵はFirestoreへ保存せず、最終確定時に入力を削除し、未処理入力も受付期限後の削除対象にする。詳細は[永続受付と実行境界](security/paid-analysis-queue-2026-11-05.md)。ピッカーが作った一時コピーだけをキャッシュから削除し、Files等にある利用者の原本とアプリ内の保持用コピーは削除しない。AI提供元側の取り扱いは提供元のデータ方針に従い、`store:false`を即時・完全消去の保証と解釈しない。

既存の公式資料URLを持つ保存済み説明、ユーザーの周期・手順・完了履歴は保持する。新しい形式は共有契約`liflow-shared-2-draft-39`で扱う。draft38のグループは署名付きの38のまま、従来の予定・家電を読み書きできる。PDF由来の新しい共有解析は、所有者が全メンバーのアプリ更新を確認し、共有管理画面で互換更新した後だけ受け入れる。更新はメンバーを変えず、将来鍵を回転し、元の署名付き履歴をSnapshotに保持する。古い版への巻戻しは拒否する。

## 個人・共有の家電をまとめる（2026-11-01）

家電追加の個人／共有の選択は除いた。グループ参加中は一度の解析結果を共通家電として保存し、個人ライブラリにも製品情報・説明・PDFを残す。共有時の確認・保存操作は維持し、二度目の保存先選択や二度目の有料解析を挟まない。個人側で解析済みの同じ結果も、再解析せず共有保存する。既存のメーカー・型番が一致する家電は一覧で重ねて表示しない。固有の個人家電は引き続き開ける。

端末スキーマ21にPDFと共有コピーの対応表を追加した。家電の保持では個人の家事定義・周期・有効状態・担当・完了履歴をコピーも上書きもしない。個人で付けた家電名を保持し、グループ退出・共有側の削除でも既に保持した個人コピーを消さない。家電一覧だけを更新する経路を使い、予定全体を再計算しない。

共有契約`liflow-shared-2-draft-42`では、PDFを最大96KiBのバイト列ずつ分割し、各片と全体のSHA-256を検証する。暗号文は通常のOutbox・署名・受付記録・Snapshotを通す。PDFの不足、改ざん、異なるアカウント、別グループを拒否する。再送は同じ内容を再利用し、同じ家電を重複作成しない。従来のdraft-41の一般予定も継続して受信できる。新しいPDF付き解析の前に共有版の対応を確認し、未対応なら有料APIを呼ぶ前に止める。

以前の版で原本を保存していなかった家電から、失われたPDFを復元することはできない。保存済み説明・履歴はそのまま使える。後から同じPDFを保持できた場合は、製品情報を変更しなくても原本の保存を補完する。新規端末は追加イベントがなくても検証済みSnapshotからPDFを復元する。

### 保存・共有の追加検査

検査用に生成した架空PDFを使い、利用者の端末内ファイルや有料AIの実APIを使わずに確認した。端末でPDFを選ぶ操作と、選んだPDFを別の共有メンバーの端末へ転送する処理は別の段階である。「後から届く」は後者の受信順序・通信切断・Snapshot復元を指す。

最大6MiB／64分割、途中欠落・改ざん・不正base64・別のdigest、逆順・重複受信、保存途中の失敗、アカウント変更・別グループ、個人の名前・家事・設定・履歴の保持、共有からの削除後の保持、遅れて受信したPDFの補完、新しい端末のSnapshotだけからの復元を自動検査した。元の不具合は修正前に失敗する回帰として再現し、修正後に確認した。追加の端末互換検査を含めて9件とした。

Auth／Firestore Emulator上の106件の結合検査も成功した。実際のRules・署名・暗号化・不変な受付記録を使い、PDFが暗号文だけで保管されること、未認証・別グループからの取得拒否、送信応答が失われた後の同一イベント再送と復元を確認した。実サービスに大量の要求を送る検査ではない。

### 端末のバイナリ処理の互換性

ブラウザーの`atob`／`btoa`がない環境を再現すると、PDFの保存前処理が失敗した。既存依存にも含まれる`base64-js`の1.5.1を明示的な依存として固定し、ブラウザー用グローバルに依存しないバイト列処理へ置き換えた。不正な形式と非正規表現は再エンコードの照合で引き続き拒否する。

共有ソース契約をdraft-43へ進めるが、PDFの形式とdigestはdraft-42と同一であり、42のPDF保存・カレンダー機能も継続して受け入れる。42のグループに再解析や互換更新を強制しない。修正前の失敗と修正後の往復成功を回帰検査に残す。

## サーバーの境界

Firebase Admin SDKの`verifyIdToken(token,true)`で署名・プロジェクト・期限・失効・無効化を検査し、Google／Appleだけを許可する。さらに正規端末検証を必須にする。認証前に有料処理を始めない。他人のjob IDは不在と同じ404。旧同期型`/analyze`からの迂回は不可。

公開の `POST /api/appliance-care/jobs` はBearer認証、`x-idempotency-key`、端末で暗号化したバイナリ本文を受け付ける。`GET /api/appliance-care/jobs/:id` は本人だけ、`GET /api/appliance-care/usage` は同期済みの本人の残回数だけを返す。`/health` は公開構成の秘密や設定状態を返さない。 [暗号化と鍵の設定](security/paid-analysis-queue-2026-11-05.md)

Firestoreの`applianceApi/v1`配下で、月次のアカウント・端末使用数、日次全体使用数、job、再利用先、実行予約、消費／返却の判断と使用数の根拠を管理する。上限照合のMAXと受付時の加算を不変な参照として残し、後から返却が起きてもコピー済みの使用数を再計算できる。正常な別の受付まで無料にしたり、同じ障害で二重に枠を増やしたりしない。

全クライアントの直接read/writeをRulesで拒否する。AdminはRulesを迂回するためホストのIAMを別途保護する。アカウント／端末枠・job・暗号化入力は1トランザクションで確定し、独立ワーカーの実行開始を確定した後だけAIを始める。job・再利用先は7日、使用数と消費／返却の根拠は対象期間終了後90日保持。結果を削除した後も返却の証拠を失わない。期限切れ削除は私的collectionごとに最大50件を取得し、1バッチ最大500件の更新時刻付き削除で新しい値の誤削除を防ぐ。共有家事や個人Plannerは削除対象に含めない。

OpenAIの鍵と復号鍵は解析ワーカー側に設定する。端末は暗号化用の公開鍵を使う。APIホストはHTTPS、入口の要求制限、ログの秘匿を備え、解析は独立したジョブで実行する。ワーカーの稼働と受付に使われた鍵への対応を確認してから、新しい利用枠を確保する。

Androidは、従来の端末署名鍵と、サーバー発行のチャレンジを含む別のハードウェア鍵で同じ要求に署名する。サーバーはGoogleを信頼ルートとする証明書チェーン、失効情報、鍵の用途、セキュアハードウェア、起動時の状態、アプリID、Play App Signingの署名を照合する。Play Integrityの応答も同じ要求に結び付ける。サーバーに保存するのは検証済みの公開鍵、失効照合用のハッシュ、許可したアプリ署名、証明期限。証明書は初回と更新時にだけ送信する。証明期限や署名鍵の更新後も従来の端末署名鍵が保たれる限り、当月の利用枠を引き継ぐ。 [Androidの鍵証明](https://developer.android.com/privacy-and-security/security-key-attestation)

Googleのルート証明書の更新時は [Google公式のルート一覧](https://android.googleapis.com/attestation/root) を照合して `android-hardware-attestation-roots.json` を更新する。失効リストは [公式の失効情報](https://android.googleapis.com/attestation/status) の有効期間内だけ再利用する。期限後に取得できない間は端末照合を一時停止する。

旧端末の出荷時に書き込まれた鍵は、Googleが指定するルートと証明書チェーンの形式に一致する場合に限り、発行側の証明書の期限切れを許容する。信頼ルートへの署名、失効、アプリとチャレンジの照合は引き続き行う。遠隔配布された証明書は有効期間も確認する。 [Googleの旧端末向け取り扱い](https://developer.android.com/privacy-and-security/security-key-attestation)

## 検査と公開までに必要なこと

1. `npm ci`と`npm run api:install`を実行し、`npm run check`を通す。Admin SDK／PDF parserはサーバー専用packageへ隔離している。
2. Auth／Firestore Emulatorの`demo-liflow-sharing`でクラウド検査を行う。本番へ攻撃・負荷要求を送らない。
3. iOSは配布用App IDのApp Attestを設定し、サーバーへ `APPLIANCE_CARE_APPLE_TEAM_ID`、`APPLIANCE_CARE_DEVICECHECK_KEY_ID`、`APPLIANCE_CARE_DEVICECHECK_PRIVATE_KEY_FILE` を渡す。DeviceCheckの2ビットはLiFlow用に確保する。AndroidはPlay Integrityのプロジェクト連携、Device Recallの承認と有効化を確認する。bitFirstをLiFlow用に確保する。サーバーには `APPLIANCE_CARE_ANDROID_PLAY_CERT_SHA256` と専用の `APPLIANCE_CARE_ANDROID_DEVICE_ID_KEY` を設定し、Play Integrityを照会できるサービスアカウントを使う。短い署名付き証明の `APPLIANCE_CARE_DEVICE_SECRET` は別の鍵を使う。
4. 実端末でアカウント切替、再インストール、翌月解除、配布署名の違うアプリ、コピーした保存データの拒否を確認する。現段階で本番Apple／Googleの応答を使う検査は未完。
5. Firebaseプロジェクト、最小権限のADC／Workload Identity、サーバーSecret、HTTPSホストを設定する。匿名認証を有効化する必要はない。本番でAuth／Firestore Emulator設定を認めない。
6. アプリに `EXPO_PUBLIC_APPLIANCE_CARE_API_URL`、`EXPO_PUBLIC_APPLIANCE_CARE_UPLOAD_KEY`、`EXPO_PUBLIC_APPLIANCE_NATIVE_PROOF=required` を設定する。Androidでは `EXPO_PUBLIC_APPLIANCE_PLAY_PROJECT_NUMBER` も指定する。通常の家電追加画面からPDFを送り、カレンダーに移動した後も解析結果を受け取り、SQLiteに保存した後で受領を返す。接続先は設定済みのHTTPSベースURLに固定する。
7. 同一の `server/appliance-care-api` イメージを2サービスに配備する。HTTPSの背後で `node src/public-index.mjs` を実行し、APIとは独立して `node src/analysis-worker.mjs` を定期起動する。ワーカーの起動間隔を稼働確認の有効期間（90秒）より短くする。鍵の対応関係とストアの利用権を照合してから、実機のPDF解析で受付、結果表示、受領まで確認する。 [ワーカーと鍵の配置](security/paid-analysis-queue-2026-11-05.md) · [ストアの利用権検証](subscription-implementation-2026-11-02.md)

この検査は開発工程内の検査であり、独立した第三者監査ではない。実施した範囲と未完の本番端末検証を分けて記録する。

## 後続の検査記録

- iOSシミュレーターのRelease版でPDFピッカーの起動・キャンセル、未確認時の解析停止、元の共有ホームへの復帰をXCTestで確認。個人DBの家事・家電・履歴等16テーブルは検査前後で一致した。有料の実APIは呼び出していない。
- Android 10実機へデータを保持してRelease版を上書きし、開発サーバーなしの起動（cold launch 2,150ms）、従来の共有ホーム、個人用PDF解析画面、Android標準PDFピッカーの起動・キャンセルと未確認時の解析停止を確認。実サービスの正規端末証明は未接続であり、実際の再インストール・有料解析のE2E完了とは扱わない。
