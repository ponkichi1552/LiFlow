# 本人用Calendarの同時再送と取得順

2026-10-30、個人アカウントの非公開リポジトリへ移した後のCIで、同じ署名済み端末設定を2台から再送するテストが失敗した。移行に伴う設定不足ではなく、既存のFirestore Web SDKトランザクション内で異なる版の文書を読める順序が原因だった。

端末設定の現在位置と、変更の不変な受付履歴は原子的に更新している。しかし並列の2回の取得が別端末の確定をまたぐと、「更新前の現在位置＋更新後の履歴」またはその逆を受け取る。独自の競合判定が先に例外を出し、SDKが文書版の変化を検証して再試行するところまで到達しなかった。

対応する版が一致しないときだけ古い側を同じトランザクション内で再取得する。版が変わっていればSDKが既存の上限付き再試行へ進む。履歴の完全一致、所有者・信頼元・署名の確認は維持する。異なる変更の競合を最後の更新で上書きしない。Rules、暗号形式、保存済みデータの変更は不要。

検査には実Firestore SDKとローカルEmulatorを使用し、一方の文書取得後、もう一方の取得前に別クライアントを確定させた。修正前のコードでは取得順の両ケースとも失敗し、修正後はSDKの再試行を経て同じ受付を回収した。履歴は2件のままで、余分なリビジョンは作らない。この2ケースを必須Cloud回帰へ登録した。

- `npm run check`：lint・型検査・通常テスト2,325件成功。
- `npm run test:sharing-cloud`：Emulator上の89件成功。異なる変更の競合拒否、他アカウントからの拒否、鍵更新、復旧処理も含む。
- 検査対象は今回公開する`main`の内容。進行中の画面・テーマ変更は別途保持し、この修正の公開には混在させていない。

これは制御した同時実行の再現検査であり、新しい実機バックグラウンド実行の観測ではない。実機での既存記録は[Release検査](21-v2-only-and-release-validation.md)を参照。
