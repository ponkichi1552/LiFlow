# 個人・共有カレンダーとGoogle Calendarの検証

対象は2026年11月1日の `main`。開始時のコミットは `c82acb049e7efe14b3ccb5dc67414bd3f0b0e3a4`。
修正前に個人SQLite、共有の署名・復号・権限判定、表示、家事の推奨、通知、Google連携までの経路を確認し、再現結果を記録した。

## 実装されている連携の範囲

- 個人予定：端末のSQLiteへ保存し、追加・編集・削除をGoogle Calendarと双方向同期する実装を追加。接続は初期OFF。接続後はアクセス可能なカレンダーを自動検出し、新規の個人予定はメインカレンダーへ送る。
- Google側の共有カレンダー：本人の個人予定としてのみ取り込む。LiFlowのグループへ予定名・場所・メモを送らない。閲覧権限だけの予定は、SQLiteの保存処理でも編集・削除を拒否する。
- FreeBusy取得は従来の経路を維持する。予定データの双方向同期とは別の権限・状態として扱う。
- グループ共通の一般予定：暗号化した変更イベントとして同期。全員が追加でき、作成者と管理者が編集・削除できる。
- 共有予定のGoogle表示：初期値OFF。選んだGoogleカレンダーへの一方向の追加・更新・削除。Googleでの変更を共有データへ逆流させない。
- Google Tasksは別の連携。Calendarの書き込み先や共有家事の権限に代用しない。

個人予定の双方向同期は、SQLite・HTTP・ネイティブ認証ゲートの自動検査に加え、iPhone・Android 10のReleaseと実Googleアカウントで、別のGoogleクライアントとの変更・削除の往復を照合した。確認したシナリオと残る範囲は末尾に記載する。

### 個人予定の差分同期

- 初回はGoogleのページを順に取得し、各ページと次の取得位置を同じSQLiteトランザクションへ保存する。以後はカレンダーごとの`syncToken`で変更・削除された予定を取得する。トークンが失効した場合だけ再走査し、未送信の個人編集は消さない。
- 送信候補はSQLiteの更新番号で絞る。変更のない1,000件では定義JSONを読み直さず、Googleへの書き込みも0件。1件の編集はそのGoogle IDへのPATCH1件で更新する。
- 繰り返し全体が未変更でも、新しく作った「今回だけ」の変更を見落とさない。例外の追加・移動・取消・リセットは同じ系列／対象回と結び付ける。
- 同時編集はETagで検出し、両方の内容を保持する。送信の成功応答が届かなくても、保存前に予約した同じIDで照合して重複を防ぐ。Googleの参加者・会議情報など、LiFlowが編集しない項目は維持する。
- 受信Inboxは索引で最大26行だけ読み、1回のトランザクションで最大25件を適用する。ネイティブの本人確認はトランザクションの前後に行い、途中のアカウント変更では全行をロールバックする。
- 自動同期は20秒、手動操作は90秒の処理予算を設け、既存workerも割り当てられた期限に従う。JavaScriptの同期計算が詰まる場合、経過時間が予算内に必ず収まる保証ではない。1回のGoogle要求は最大100回。取り込み中でも未送信編集のための時間と要求数を残し、残りは保存した位置から再開する。
- 同期日時・エラーだけの通知では家事やカレンダーを再計算しない。地域ごとの日付境界も、地域と日付が同じなら再計算せず、夏時間や日付が飛ぶ地域の結果を維持する。

## 再現して修正した問題

| 問題 | 再現と修正 |
| --- | --- |
| 共有の一般予定が家事配分へ入らない | 共有の終日予定がある日へ重い家事の推奨が残った。表示・固定日時の確認・通知・共有Tasksに同じ共有カレンダーの入力を渡す。グループの正式日時は書き換えない。 |
| 複数の予定情報を重ねた時の過少集計 | 3つ目の入力で時間帯の情報が失われ、離れた予定を最大値だけで数えた。正確な時間帯を持つ入力同士は和集合を維持する。時刻のない家事には時間帯の競合判定を行わない。 |
| Googleの保存成功後に通信が切れると再送が止まる | Googleが省略する空文字・既定値・RRULEの順序を単純比較していた。意味を比較し、同じ予定の保存済み応答を照合する。外部で変更された内容を勝手に上書きしない。 |
| 更新した予定を別のインストールから重複作成する | 更新時にも出所とリビジョンの証明を更新し、同じGoogle IDを復旧できるようにした。証明や内容が一致しなければ競合のまま保持する。 |
| カスタム繰り返しの最初に余分な予定ができる | 実Google Calendarでも、BYDAYに含まれない開始日が1件表示されることを確認。最初の実施日にDTSTARTを合わせ、週・月の間隔の基準を維持する。期限内に対象日がない系列は作らない。 |
| 移動した繰り返し予定の対象回を見失う | 変更先の地域で元の日時を解釈していた。親系列の地域でoriginalStartTimeを照合する。 |
| Googleの同意画面を読むと接続がタイムアウトする | Android実機で20秒を超えて同意した後に再現。同意操作の時間と、その後の一覧取得の20秒制限を分離した。 |
| 手動同期が履歴の検証中に時間切れになる | 自動処理と同じ20秒の制限に当たった。明示的な手動操作だけ最大90秒とし、既存workerの期限は延ばさず、後続の処理として実行する。100要求の上限と自動・背景処理の最大20秒は維持する。 |
| 同じ同期中に毎回ネイティブのトークン取得を呼ぶ | 100 HTTP要求で100回取得していた。制限時間内のAPIインスタンスに限って共有し、各要求前後の本人確認は維持する。401後や別の同期へは持ち越さない。 |
| 再読込と例外予定の走査が過剰 | 変更のない定義も毎回解析・地域検証し、各予定が全例外を走査していた。DB接続ごとの検証済み行と、予定IDごとの例外索引を使用する。生データや更新番号の変化、削除、不正なJSONは引き続き検出する。 |
| 個人予定に保存できない分類を選べる | グループ専用IDを個人用の選択肢から除外した。共有用に作成中の分類も、そのグループに限定する。 |
| 同期状態の通知だけでカレンダーを繰り返し再計算 | Android実機で計算途中の無効化が連鎖した。同期日時と終了通知だけの更新を区別し、予定や権限が変わった時の再計算は維持する。アプリ全体の所属確認にも同じ区別を適用し、50回の状態通知で増えていた50回の所属読込も防ぐ。古い計算結果を最新結果として公開する制約は緩めない。 |
| 過去のアクセスエラーで所有者の閲覧も止まる | 読込前のカタログ更新が書き込み制限に当たった。認証済みのローカル閲覧を継続し、編集は従来どおり拒否する。 |
| 以前の検査用グループが端末とクラウドで異なる | iPhoneに古い表示先が残っていた。同期時にクラウドの現在の所属と、端末に保持した承認済みv2データを照合して表示先だけ復旧する。知らないグループへ自動参加せず、旧DB・履歴・未送信操作を削除しない。 |

ネイティブの初期配置・編集画面の終了中の古い可視行通知では、明示的に選んだ月を変更しないよう保護した。指で閲覧した月への追従は維持する。

未確定の共有予定は空き時間として扱わない。分類や下書きの変更だけで家事配分を作り直す既存動作も増やしていない。

## 動的検査

実Googleサービスへの大量要求は行わない。大量データ・意図的な切断・権限違反は、独立したSQLite、ローカルHTTP、Auth／Firestore Emulatorで実行した。

- 独立した日単位の列挙と、本体の繰り返し計算を4,096組で照合。日・週・隔週・月・年、複数曜日、第N曜日、月末、終了日を含む。
- 実際のローカルHTTP通信で1,052件を100要求以内ずつ11回に分けて送信。50個の同時呼び出しをまとめ、未変更時とOFF時にはHTTP要求0件を確認。
- 保存後にソケットを切断する疑似Googleサーバーで、追加・更新・削除の再送と重複防止を確認。単純な関数モックの成功だけでは判定していない。
- Google応答の省略値、RRULEの並べ替え、412／409、改変・キャンセル済み応答、Retry-After、アカウント変更、短い実行期限を検査。
- Firestore Rulesと実際の暗号化・SQLiteを使う2利用者で、12系列の追加、オフライン再起動、作成者と管理者の同時編集、明示的競合解決、今回だけの移動・削除、系列削除、除名後の拒否を検査。共有家事の正式日時が変わらないことも照合。
- 個人SQLiteの隔週・終了日・例外・削除を、共有家事の本人向け推奨まで通す。個人予定名・場所・メモが共有モデルへ混ざらないことを確認。
- iOS／Androidの画面ハーネスで、分類の保存先分離、50回の状態通知で再計算しないこと、実データ更新とアカウント変更時の再確認を検査。
- 1,000系列と20,000例外で走査量を確認。10,000件のDBでは、同じ更新番号でも生JSONが変われば検証をやり直す。

実Google Calendarには検査用の系列だけを作り、開始日と複数曜日の結果を照合した。検査後に系列を削除し、検索結果0件を確認した。通常の予定は変更していない。接続ツールによるこの結果と、LiFlowアプリのネイティブOAuth経路は区別する。

### 共有の実削除とデータ保護

Auth／Firestore Emulator112件の成功後、対象プロジェクトのFirestore Rulesだけを配布した。配布前のRulesは当時のHEADと一致し、配布後はローカルのRulesとのSHA-256一致を再取得して確認した。旧Rulesと更新前のiPhone Documents・DBを非公開の検査用保管先へ退避した。48DBは、WALが必要なものを隔離コピーで開く検査も含め、復元可能な状態で確認した。

既存の検査用グループは所有者の通常画面からdraft46→47へ更新し、両端末で同じ版を確認した。その後、実サービスで全メンバー確認済みの期限整理が進み、保持境界2026-10-01・鍵世代9→10・Snapshot位置368→371を照合した。保管先の件数はイベント32→3、受付172→137、Snapshot3→1、分割Snapshot10→2となった。iPhone・Androidの両端末でも鍵世代10と期限整理の保存状態を確認した。件数だけを個別履歴の削除証明にはせず、期限・署名・合意・削除後の復元は暗号化した複数利用者の結合検査でも照合している。

### 待ち時間と重複処理

Android 10の同じ実機・診断OFFのReleaseで、起動操作からホームの実際の家事をタップし、説明が開くまでを5回測定した。ホーム検出は5,331／5,295／5,247／5,311／5,302ms、中央値5,302ms。タップから説明の検出は中央値1,548msだった。自動操作の検出待ちも含むため最初の描画時刻そのものではないが、1秒の目標を達成した結果ではない。

追加診断では、共有状態の読出し・検証が初回に長くかかり、共通Schedulerだけを速くしても全体は解消しないことを確認した。保存された名簿が同じ場合の重複検証を減らし、11回の同内容の読み取りで署名検証11回→1回とした。SQLite自体は毎回読み、内容変更・別ハンドル・改ざん・アカウント不一致・削除は引き続き検査する。返すオブジェクトを共有せず、保持は1ハンドルあたり上限付きの1行だけ。変更を含む最新Release・診断OFFで同じ5回の手順を再測定すると、ホーム検出5,335／5,250／5,305／5,142／5,299ms（中央値5,299ms）、説明検出までのタップ後時間は中央値1,418msだった。ホームの結果は実質横ばいで、この変更によって起動目標を満たしたという結論にはならない。説明を開く手順の計測であり、完了の確定・Google反映の完了時間は含まない。

個人予定だけが変わり、署名付き共有入力・受付・未送信状態・表示期間が同じ場合は、共通家事の計算を再利用する。毎回の権限確認は維持し、設定変更・改ざん・除名後に古い計算を使わないことを検証した。同期状態だけの通知では画面や家事を再計算しない。

起動順にも競合があり、保存済み表示の復元前からPlanner・個人カレンダー・事前取得のProviderが動いていた。所属・保存表示の選定を先に済ませてから、それらを開始するようRootのProviderを並べ替えた。両OSの実際のRoot配線を使う回帰テストは修正前に失敗し、変更後に通過。iPhone実機とiOSシミュレーターのRelease主要画面検査も再度PASSした。

この変更後の診断OFFのAndroid Releaseで同じ5回の手順を測定したところ、ホーム検出4,437／4,260／4,275／4,316／4,280ms（中央値4,280ms）、タップ後の説明検出は1,792／1,744／1,686／1,705／1,773ms（中央値1,744ms）だった。ホームは約1秒早くなった一方、タップ後は前の測定より遅く、表示後の仕事の干渉まで解消したとはいえない。1秒以内の起動目標も未達。両端末には診断OFFのReleaseをデータを残して導入している。
