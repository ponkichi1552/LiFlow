# 確定している設計方針

- ユーザーの追加操作を発生させない。通常の完了操作と、既存の設定・履歴から自動調整する。

- 汚れ具合の評価、変更提案への承認・拒否、理由の追加入力を最適化の前提にしない。

- 周期にアプリが決めた上限を設けない。家電も例外にしない。

- 初期周期が14日でも、本人の実施ペースが約60日なら、そのペースへ適応できるようにする。

- 完了履歴はそのユーザーの行動の一部分であり、家全体の実施履歴ではない。同居人による普段の手入れや分担の約束を、アプリが把握していると仮定しない。

- ごみ収集日は、ユーザーが設定した日を表示するだけ。完了操作、実施履歴、周期学習、期限切れの対象にしない。粗大ごみの日も、実際に出すことを前提にしない。

- 7日以内は期間表示なし、8〜13日は±1日。14日以上は後述の段階表を初期値として採用する。

- 期間のある重い家事は、有限探索の範囲で登録休日を含む期間を探す。おすすめ日は平日でもよく、休日への負荷集中を避ける。休日なし・候補なしの場合は後述の通常配置または原位置フォールバックを使う。

- 期限切れを失敗として強く扱わない。現在の方針は、他のカードより多少強調する程度で、存在感を大きく変えない。

- 周期更新は完了操作や明示的な周期・モード変更をきっかけに行い、日付経過や画面再描画だけでは変更しない。

- 数値周期を持つ個人の通常家事だけを自動学習する。表示期間内の完了なら維持し、期間外または期間表示なしの完了で再計算する。初回の有効3間隔が揃うまでは初期周期を使う。個別固定・共有・季節固定・必要時型・ごみ表示は学習対象外。

- 最大参照間隔数は周期に応じて8・6・4とし、新しい履歴を重く扱う。期間内の記録も推定に含める。

- 登録された予定がない日は配置候補にする。未登録の用事や急な忙しさへの余裕は、実施期間で持たせる。

- 期間を広げられる上限に達したら基準日を移動する。移動先では拡張幅を引き継がず基本幅へ戻す。

- 曜日による休日設定に加え、日付ごとの休日設定に対応して不定休の人も扱う。追加の入力を最適化の必須条件にしない。

## 初期周期のモード

- **こまめ**：汚れがたまる前に手入れしたい人向け。メーカー等の推奨を参考に、短めの周期。

- **標準**：実態調査と手入れの必要性を両方見て、無理なく続けやすい周期。

- **最低限**：標準より間隔を空け、まとめて行いたい人向け。ただし汚れ・におい・機器の表示があれば前倒し。

各モードの具体的な家事周期は家事一覧側の値を利用し、全家事共通の倍率で定義し直さない。数値周期のない「収納前・汚れ時」等のモードは必要時型とし、定期通知・周期学習・次回日予測を行わない。汚れや使用状態の検知を仮定せず、そのための新規入力を作らない。

「使用中3か月＋収納前」のような複合記述は、3か月という定期部分と収納前の手順・注意説明を分ける。使用状態を取得していなければ、使用開始・終了を勝手に推測して周期を起動・停止しない。「使用後」等を1日周期へ変換しない。

# 適用対象と共有家事の境界

- 自動周期学習は個人の通常家事に適用する。個別に指定した周期は固定する。季節の切り替えが目的の家事は固定日型へ分け、周期の入力・学習・モード倍率を使わない。

- 共有家事は学習しない。現行V2の共通基準日・共通周期・共通期間を保持し、個人へのおすすめはその共通期間内で扱う。個人の履歴から共通計画を変更しない。

- 共有側で指定した日時と個人の予定が衝突しても、今回の学習設計によって共有指定を勝手に変更しない。期間延長の既存承認フローも変更しない。

- 共有の完了記録は完了状態や短い再提案抑制には使われるが、周期学習へ流用しない。

# 処理構成

個人の通常家事の自動最適化が以下の対象となる。個別固定周期、共有の共通計画、季節固定日、ごみ表示はそれぞれ専用の分岐へ渡し、通常家事の学習を通さない。

1. 新設計の家事データ・初期設定と、運用開始後の有効履歴を読み込む。旧開発データの変換は行わない。

2. 現在の確定周期を保持し、完了時などの更新条件を満たした場合にだけ実施間隔から再推定する。

3. 日数型は実施日と確定周期から次回の元の基準日を計算する。暦型は対応する回の暦規則から次回を計算する。

4. 8日以上の周期なら基本の実施期間を作る。

5. 登録された予定・時間上限・負荷・休日を見て期間を拡張する。上限で足りなければ基準日を移し、基本幅へ戻して候補を探す。

6. 複数の家事の負荷と作業時間をまとめて見て、おすすめ日を配置する。

7. 完了されるまでその回を保持し、完了後に次回を作る。

8. 完了時、表示期間内なら周期・暦規則を維持する。期間外または期間なしなら、有効3間隔以降に再推定する。日付経過だけでは変更しない。

# 家事ごとに持つ情報

- 選択されたモードに対応する初期周期。

- 通常の完了操作で記録された完了日。

- 履歴から計算した現在の周期。

- 家事の負荷と実作業時間。

- 周期から求める元の基準日、配置調整後の基準日、表示した実施期間、おすすめ日。

- 曜日休日と日付別の休日・勤務日。日付別設定がある日は曜日設定より優先する。

**元の基準日**は通常家事では最終完了日と確定周期から求める日、**配置上の基準日**は予定や休日に合わせて動かす日、**実施期間**はその回に表示する範囲、**おすすめ日**は期間内の実行候補、**完了日**は実施が記録された日として分ける。履歴ゼロの初回基準日は初回範囲内の固定シードで一度決める。季節固定日は地域別の固定データから選ぶ。配置調整自体では周期を変更しない。

保存項目は処理で参照するものに限定する。表示期間は完了時の内外判定、事前予測は成績評価、当時の初期周期とモードは履歴換算、操作IDと版番号は取消・重複・競合防止に使う。自由記述の「広げた理由」は保存しない。AIや外部AI APIは使わない。

# 初回の予定

履歴がない場合は、選択モードの初期周期を使う。例えば標準が14日なら、14日を出発点にする。これは学習後の周期の上限ではない。 初期の日数型へ換算するときは1週＝7日、1か月＝30日、半年＝180日、1年＝365日を既定値とする。これは家事一覧の初期値を日数へ変換するためだけの規則であり、採用中の暦規則やモード変更時の合意済みの実暦日数計算を置き換えない。

## 初回配置の方針

- 実施済みと仮定した履歴は作らない。初回配置と実際の完了履歴を分ける。

- 負荷・予定・時間上限を見ながら分散して自動配置する。軽い家事にも時間や配置の偏りを考慮し、件数制限がないことを理由に全部を今日へ置かない。

- 季節の切り替えが目的の家事は、周期の長短では分類せず、地域別の固定日へ配置する。季節性のない家事に季節を作らない。

- 季節固定型以外の初回は、今日を含む min(初期周期, 30) 日間をまず探す。配置できず初期周期が30日を超える場合だけ、今日を含む1周期分まで広げる。長周期でも季節性がなければ同じ処理。初回基準日は最初の範囲内で利用者・家事・初回配置版による固定シードから一度だけ選び、全候補が不適合な場合はその日へ置く。初回探索範囲は周期上限ではない。 毎日設定の家事には日付固定ルールを優先し、負荷分散や候補不足を理由に別日へ移さない。

季節の切り替え自体が目的の家事は次の該当固定日まで待ち、初回だけ別の季節へ置かない。単に作業しやすい季節がある通常家事は、初回候補期間との重なりを優先し、重ならなければ通常配置にする。[エアコン試運転](https://panasonic.jp/aircon/contents/tips/season-trouble/test-run.html)の推奨時期をエアコンの全手入れへ転用するなど、異なる作業の根拠を流用しない。

# 完了履歴からの周期計算

## 履歴の整理

- 同じ家事の完了日を時系列に並べ、日付間の正の間隔を計算する。

- 同じ家事の同じローカル実施日の有効完了は、学習入力・予測採点・交互位相を共通の1単位へ集約する。原本は残す。代表は最初に有効として確定した完了とし、その事前予測・表示期間を使う。後続の同日記録で学習や位相を重ねて進めない。

- 完了取消では、その完了が生んだ履歴・学習状態・予測成績・次回予定への影響を戻す。後から行った別の操作まで巻き戻さない。実施日訂正の新しい画面を追加することは、この設計では前提にしない。

- 長い間隔という理由だけで記録を除外しない。

- 記録がない期間を、家全体で未実施だった期間と解釈しない。

## 更新条件と参照履歴

1. 完了前にその回へ表示されていた期間を使い、完了日が期間内か期間外か判定する。予定によって拡張された後の期間を使う。

2. 期間内なら周期・暦規則を維持する。期間外、または期間なしの場合は、有効3間隔以降に再計算する。個別固定・共有・季節固定・必要時型・ごみ表示は対象外。

3. 再推定する場合、前回確定した周期から最大参照数を一度だけ選ぶ。同じ完了処理の中で、計算結果を使って参照数を選び直さない。

4. 期間内・期間外の両方を含む有効な直近の実施間隔を、新しい履歴ほど重くして計算する。期間外の記録だけに限定しない。

5. 更新対象なら採用中の方式のパラメータを再推定する。方式自体の変更には後述の比較条件も必要。日数は丸め前の値を保持し、日付計算に使う段階で小数点以下を切り捨て、1日未満なら1日にする。

## 最大参照数

- 前回確定した代表周期が30日以下：最大8間隔。

- 31〜90日：最大6間隔。

- 91日以上：最大4間隔。

「間隔8件」には通常9個の完了日が必要。有効3間隔から学習し、最大数まで待たない。参照数の境界だけ30日・90日を使い、暦モデルの次回日付を30日固定で計算する意味ではない。

重み付き中央値を初期方式とする。有効な直近k間隔を古い順にi=0〜k−1とし、重みは w_i=1+0.5×i/(k−1)。各記録ごとに階段状に増え、最古1、最新1.5となる。値を昇順に並べ替えて重みの累積が全体の半分へ到達する値を採用する。ちょうど半分なら、その値と次の値の平均を使う。学習開始前のk<3では適用しない。

多い履歴は安定した生活では推定のばらつきを抑えられる一方、生活変更への追従を遅らせる。件数と新旧の重みを合わせて検証する。履歴は削除せず、計算で参照する範囲と評価用の記録を区別する。

## 更新条件の例

- 初期14日から約60日間隔へ変わり、期間外完了が繰り返される場合：初期値からの変更上限を設けず、そのペースへ追従できる。具体的な到達速度は重み付けと採用方式に依存する。

- 14日周期で毎回16日目に完了し、その日が毎回表示期間内の場合：周期は14日のまま維持し、実際の完了日から次回の基準日を作り直す。数字を実測平均に一致させるより、期間内で無理なく実行できることを優先する。

- 初期14日で、その後完了記録がない：経過日数を新しい実施間隔として追加しない。

- 8日周期の重い家事を7日目の休日に完了しても、その日が表示期間内なら8日周期を維持する。アプリの休日配置だけを理由に7日へ短縮しない。

# 予測方式の比較

以下の4方式を、それぞれ必要な履歴・適用条件を満たす場合に比較する。複雑な方式を最初から無条件に採用せず、同じ完了に対する事前予測で評価する。

- 新しい履歴を重くした中央値：直近8・6・4間隔を使う基本方式。

- 有限窓の指数重み付き平均：新しい間隔へ追従する比較候補。標準的な指数平滑法をそのまま使うのではなく、新旧の重み上限1.5倍を守る。

- 曜日・暦方式：隔週土曜や月末などの日付パターンを扱う比較候補。

- 交互間隔方式：7日・21日などが交互に現れる場合の比較候補。

## 予測方式の比較方法と初期判定値

1. 各方式が前回の完了時点で予測した次回日付と、今回の完了日を比較する。

2. 同じ評価機会で何日ずれたかを記録する。

3. 今回の完了を履歴に加え、各方式が次回日付を予測する。

4. 複数回の事前予測の成績から、採用候補を選ぶ。期間内完了では評価だけを更新し、実際の周期は維持する。

5. 周期更新が許される完了時のみ切り替えを適用する。期間内なら評価を蓄積しても、周期・暦規則は変更しない。

次回予測日を同じ有効完了単位で評価する。予測は前回の有効完了処理時に保存し、配置で動かす前の値を使う。履歴へ後から当てはめた誤差を事前予測の実績へ混ぜない。

予測用の直近8・6・4間隔、過去の予測誤差、完了履歴の原本を分ける。処理は対象家事の完了・訂正時などに限定し、画面表示のたびに全家事の全履歴を再計算しない。4方式は通常の数値処理であり、4つのAIや並列サーバーを必要としない。

比較は候補ごとに、採用中方式と双方が事前予測を残した同一比較区間の直近3回で行う。全候補の予測が同時に揃う必要はない。学習開始の「3間隔」と、評価できる「3回分の事前予測」は別条件である。

- 評価は予測日と実施日の絶対誤差を使い、古い順に1、1.25、1.5の重みを付けた平均誤差で比較する。

- 候補方式が3回中2回以上で現在方式より誤差が小さいこと。

- 重み付き平均誤差が現在方式より20％以上、かつ0.5日以上小さいこと。

- 条件をすべて満たす場合だけ方式を変更する。等号は20％・0.5日の改善条件では合格、各回の勝敗では同点扱い。現在方式の誤差が0なら変更しない。これらは設計初期値であり最適性は未実証。旧「周期の6割・8割」は使用しない。

# モード変更

## 合意した計算式

**変更後の周期＝変更前の周期×新モードの初期周期÷旧モードの初期周期**

倍率式は変更前後の両モードに数値初期周期がある場合だけ使う。全家事共通の倍率や一律加算ではない。初期値が3日・7日・14日で、標準の学習済み周期が10日なら最低限への変更後は20日となる。定期型から必要時型へ変えたら新しい定期候補と周期予測の生成を停止し、履歴は残す。必要時型から定期型へ戻したら、そのモードの初期周期から既存の初回配置規則で再開し、必要時型をまたぐ間隔を学習に使わない。ゼロ除算や架空の初期周期で倍率を作らない。全体モード変更時も今日・明日の現在回は保護し、変更後の周期・必要時設定は次回生成へ反映する。本人がその予定を直接変更した場合は明示操作を優先する。

## 過去履歴の引き継ぎ

過去の実施間隔を、その当時のモードの家事別初期周期に対する比率へ変換して保持し、新モードの初期周期で換算する。過去履歴を消さず、変更後の完了も反映する。

モード変更をまたぐ1間隔は記録を残すが周期学習の計算から外す。異なるモードにまたがる間隔を片方へ割り当てない。

- 丸め前の値を持ち、モードを往復するだけで丸め誤差が累積しないようにする。

- 初期周期が同じモード間では倍率1とし、無理に差を作らない。

個別固定周期を最優先する。20日固定ならモードを変えても20日を保ち、自動学習しない。固定解除は現在モードの初期設定へ戻し、数値周期のあるモードでは新しい学習区間の3間隔から再開する。現在モードが必要時型なら定期候補を生成しない。過去記録は削除しない。家事の無効化解除は残っている有効履歴から再計算するが、必要時型に周期を作らない。無効化・必要時型をまたぐ間隔は学習から外す。

## 暦型からモード変更する場合

暦型で採用する規則はn週ごとの曜日とnか月ごとの月末に限定する。モード変更時は1周期分を実際の暦の日数へ換算し、モード倍率を掛けて日数型へ変換する。その後の現モード履歴から暦型を再評価する。任意の日付指定や第何曜日の自動検出は初版に入れない。

- 月次の規則は最後の実施日から1暦月、隔月は2暦月、隔週は14日を1周期として扱う。直近の月末までの残り日数ではない。

- 同じ日付がない月はその月末へ補正し、2つの日付の差を取る。表示期間の両端を含む日数計算とは区別する。

- 1周期の日数に新モード初期周期÷旧モード初期周期を掛け、最後に小数点以下を切り捨てる。

- 例：平年の2月1日から3月1日は28日。倍率1.5なら42日で次は3月15日。うるう年なら29×1.5を切り捨てて43日。完了を挟まないモード往復では、最初の変更前の丸め前値・モード・暦規則を変換基底として保持し、毎回そこから計算する。元のモードに戻れば元の規則を復元する。

# 完了から次回を作る

日数型は実際に記録された完了日を起点に確定周期を加える。通常完了ではその日の利用者ローカル日付を記録し、前倒し完了の対象予定日を実施日として使わない。次回おすすめ日は直前の有効完了日より必ず後にする。新しい遡及入力画面は追加しない。

- 早めに完了した場合、その回を完了とし、元の予定を未完了として残さない。

- 遅れて完了した場合、日数型は実施日を次回の起点にする。暦型は予定回と規則に沿って計算する。

- 例：11月1日に完了し、学習周期が60日なら、次回基準日は12月31日。

- ごみ収集日のように暦で決まる表示は、この計算から除外する。

通常家事の暦型は完了を現在の予定回に対応付ける。11月末の回を11月29日または12月1日に完了したら次は12月末。数回先まで遅れても1回の有効完了で未完了分を解消し、次の規則日が実施日以前なら実施日より後の最初の規則日へ進める。架空の完了履歴は作らない。交互型は同日の重複を集約した有効完了1単位につき位相を1つ進める。季節固定型は別の固定日表を使う。

# 実施期間の計算

- 周期7日以下：期間を表示せず、日付だけ表示する。

- 周期8日以上：基準日の前後に期間を作る。

14日以上は以下の段階表を基本幅の初期値として採用し、利用時の挙動を検証する。

- 8〜13日周期：基準日±1日、両端を含め3日間。

- 14〜29日：±2日、全体5日間。

- 30〜59日：±3日、全体7日間。

- 60〜89日：±5日、全体11日間。

- 90〜179日：±7日、全体15日間。

- 180日以上：±14日、全体29日間。

旧案の一律「周期の約10％」は使わない。通常家事が学習で長周期になれば、更新後周期の基本期間を作る。利用者が個別に指定した期間幅・休日優先・家事可能時間帯は自動処理で上書きせず、明示設定を優先する。季節固定型にこの周期由来の幅を適用しない。

## 予定による拡張と移動

1. 元の基準日を中心に基本期間を作る。

2. 登録済み予定・家事負荷・休日から候補日を探す。予定が未登録の日は候補に含め、未知の忙しさを推測して除外しない。

3. 候補不足なら前側を優先して拡張し、見つからなければ後ろ側も試す。表示全体の上限を守った独立候補として比較し、基本3日・最大4日の場合も「前へ1日」と「後ろへ1日」の両方を試せるようにする。詳しい列挙順は後述する。

4. 拡張上限でも不足する場合は配置上の基準日を移し、基本幅へ戻して候補を探す。移動先でも必要なら同じ上限内で拡張する。

5. 元の基準日と配置後の基準日を分け、期間の移動を周期の変更として扱わない。

拡張上限は基本期間の両端を含むW日×1.5を切り捨てる。3→4、5→7、7→10、11→16、15→22、29→43日。移動順は元の基準日から−1、＋1、−2、＋2…。「範囲の1.2倍」は基本期間W×1.2を切り捨てた日数を前後それぞれの最大移動量とする。拡張済み幅や移動済み地点を基準に伸ばし続けない。候補なしなら元の基準日・基本幅へ戻すが、既存予定の再配置では今日・明日の移動禁止を優先し、抵触する場合は現在の表示位置を維持する。

例：基本3日間なら拡張は最大4日間まで。そこで候補がなければ基準日を移し、3日間へ戻す。拡張済み4日間は持ち越さない。全候補不適合時の原位置復帰にも、毎日固定・今日明日保護・次回おすすめ日が完了日より後という制約を適用する。初回は前述の初回基準日へ置く。

# 重い家事と休日

期間表示のある重い家事には、登録済みの休日を期間に含める。曜日設定だけでなく、日付ごとの休日設定に対応し、不定休を扱う方向で進める。

1. 基本期間内に休日があれば、その期間を候補にする。

2. なければ、前側優先の有限探索で登録休日を含む期間を探す。休日が登録されていても、おすすめ日そのものは平日でよい。

3. 拡張上限に収まらない場合は基準日を移し、基本幅へ戻して休日を含む候補を探す。

4. 平日・休日それぞれの時間帯と合計時間上限を使う。2026年11月8日の明示決定により、未設定時の初期時間帯は平日19〜21時・休日9〜19時とし、画面にも同じ時刻を表示する。日付別指定、平日／休日別の明示設定、既存の曜日別設定、初期値の順に優先し、明示的な空の時間帯は家事不可として保持する。個別の時間帯を休日判定で上書きしない。予定を差し引いた連続空き時間が実作業時間以上あり、日別時間・普通と重い家事の件数上限を超えない日を候補とする。30分の作業を10分の空き3つへ分割しない。機器の待ち時間は実作業時間へ加えない。 家事一覧に明示された分割項目は、その項目の作業範囲・時間・負荷を使う。親の残作業量が定義されていない場合に推測して任意分割や部分完了を新設することは、今回の実装範囲に含めない。

曜日休日が少なくとも1曜日設定され、日付別の勤務日上書きがない場合、次の休日は最大6日先にある。不定休・日付別の例外がある場合は、同じ保証はない。

休日情報がない場合は土日を勝手に休日とせず、追加質問も要求せず、休日包含条件だけを外した通常配置にする。登録休日があるが有限探索内に条件を満たす配置がない場合は原位置へ戻す。

日付別設定：曜日設定を基本とし、個別の日の休日・勤務日設定があればその日だけ優先する。不定休に対応するが、日付別入力を全員に必須化しない。

休日包含と休日実施は分ける。期間に休日があれば、その休日が他の家事で埋まっていても期間内の平日をおすすめできる。日付別の勤務日・休日は曜日設定より優先する。休日が存在しない場合まで「必ず含む」とは保証しない。

# 複数家事の配置

各家事を独立して配置せず、候補期間を作った後で家事全体の負荷を比較する。登録されていない用事は推測せず、予定のない日も候補として使う。

- 同じ日に重い家事が固まりすぎないようにする。

- 件数だけでなく、負荷と実作業時間の合計を見る。

- 洗濯機の運転待ちなど、機器が動いている時間は実作業時間と分ける。

- 同じ場所の家事をまとめる処理は、予定・負荷分散・休日・距離の優先順位を崩さない同点条件に限る。初版では新しいまとめ入力を要求しない。

- 優先順位は登録予定と時間の適合、負荷分散、重い家事の休日優先、元の基準日への近さ。同じ条件なら既存おすすめ日、日付の早さ、安定IDの順で決める。

- 今日と明日の既存家事は自動再配置の移動元にも移動先にもしない。急な予定が重なっても動かさず、追加確認を出さない。完了・取消・共有完了で空いた枠へ他の日の家事を補充しない。完了からの次回新規生成、初回生成、本人が当該予定を直接変更する操作は自動移動と区別する。

予定変更では変更区間と探索領域が重なる家事、移動元・先の負荷を共有する家事を一つの対象集合として計算する。毎日固定、今日・明日、季節固定日などの保護対象は予約を固定して先に除外する。集合内の旧予約を外し同じ入力版で一度だけ計画し、集合外は動かさない。候補を再訪せず、候補なしは各家事のフォールバックへ進む。結果は一括反映し、新しい入力版が来た場合だけ再実行する。

# 期限切れと未完了

- 期間を過ぎても、その家事の未完了カードは1件のまま残す。

- 次の周期が来ても、同じ家事の未完了カードを何枚も追加しない。

- 時間が経過しただけで周期を延ばし、期限切れを消すことはしない。

- 後日完了したら、日数型は実施日を起点に、通常の暦型は対応回と規則から次回を求める。季節固定型は同じ作業種別の次の固定回へ進める。冬物収納と夏物収納など意味の異なる作業を同じ未完了分とみなして一括完了しない。

- 表示の強調は控えめとし、失敗を強く示す扱いにしない。

- 未記録から、家全体で誰も実施していないと推測しない。

# 実装する数式とモデル状態

## 日付と履歴

日付は利用者の設定タイムゾーンの暦日とし、ミリ秒差を24時間で割らない。完了日時UTC、当時のタイムゾーン、確定ローカル実施日を保存し、後のタイムゾーン変更で過去の日付を書き換えない。同一操作IDの再送と同一予定回への二重完了を排除する。異なる原本でも同じ家事・実施日は有効完了1単位に集約し、学習・採点・交互位相を揃える。

各間隔gにその期間のモードと家事別初期周期Bを対応付け、現在の初期周期B_nowへの入力を x=g÷B×B_now とする。モード変更、固定解除の学習区間境界、無効化期間をまたぐ間隔は原本を残して除外する。長いという理由だけでは除外しない。新設計の完了記録に必要値を同時保存し、欠けた値を現在値で勝手に埋めない。

期間内判定は完了対象カードが参照していた表示期間版を使う。オフライン時もその版を送信し、後着の別配置版へ置換しない。新設計では参照される期間版を保存する。必要な版が欠損する不整合時は、その完了での周期更新だけを見送り、完了記録は保持して修復対象とする。利用者に追加入力を要求しない。

## 四方式の具体化

1. **重み付き中央値**：前述の最大8・6・4間隔と1〜1.5の重みで求める。初期の採用方式。単発の長い間隔に比較的強いが、変化は滑らかとは限らない。

2. **有限窓の指数重み付き平均**：同じk件に v_i=1.5^(i/(k−1)) を与え、sum(v_i×x_i)÷sum(v_i) を求める。重み上限を満たすための設計であり、一般的な無限履歴の指数平滑法とは区別する。別の固定αを追加しない。

3. **曜日と暦**：現モード内の連続した有効履歴を使う。週候補はn=max(1, round(重み付き間隔中央値÷7))と完了曜日の重み付き最頻値を組み合わせる。同点曜日は最新の実施曜日。直近完了に最も近い該当曜日を位相の起点とし、等距離なら前。月末候補は各完了日を最寄り月末へ写像し、等距離なら前月末。正の月インデックス差が3件以上あるとき、その重み付き中央値を四捨五入したnか月を候補にする。ゼロ月差は候補推定の件数に数えず、元履歴は残す。重みは時系列順の1〜1.5を使う。任意の日付・第何曜日は生成しない。

4. **交互間隔**：現モード内で連続した有効4間隔以上、偶数番と奇数番が各2件以上あるとき各組の重み付き中央値をA・Bにする。全参照窓で付けた時系列重み1〜1.5を各組へ引き継ぎ、分割後に振り直さない。通し番号の偶奇も窓移動で変えない。A・Bの丸め後が同じなら新規候補にしない。採用中なら同値の規則を保持し通常の方式比較を待つ。次の位相は最新の有効間隔の次。期間内完了ではA・Bを更新せず位相だけ進める。

正のroundは0.5以上切り上げ。曜日型・月末型は採用後に予定回の位相を保持し、完了のたびに写像し直して規則を変えない。候補の再推定と採用中の確定パラメータは別に持つ。候補条件を満たさない回は予測なしとし、0日や初期値のダミー予測を採点しない。取消は既決の影響復元に従い、取り消した記録から得た周期を保持する特例は置かない。

参照数を選ぶ代表周期は日数型の丸め後値、曜日型7n、月末型30n、交互型floor((A+B)÷2)とする。次回の基本期間は日数型・週型ではその間隔、月末型では今回と次回の規則日の実日数差、交互型では次の番のAまたはBから求める。代表周期の近似を実際の日付生成に使わない。

## 方式切り替え

候補ごとに、採用中方式と双方が同時点に出した同一比較区間の直近3回の事前予測を、実施日との絶対誤差で比較する。全候補共通の3回を要求しない。採用中方式は当時の固定パラメータによる実予測を採点し、後から学習した影モデルへ差し替えない。候補が出せなかった回はそのペアの評価回に数えない。

期間内完了でも記録・採点・候補学習を行うが、採用中のモデルとパラメータは保持する。期間外または期間なしの完了時だけ、3回中2勝、重み付き平均誤差20％以上かつ0.5日以上改善をすべて満たした候補へ切り替える。候補が複数なら平均誤差、最大誤差、中央値・指数平均・週・月末・交互の固定順で選ぶ。

方式切り替え・モード変更・固定設定変更では比較区間IDを更新する。変更前の予測を新方式の成績へ付け替えない。原本は保持し、新しい比較は同区間の共通3回を待つ。3間隔での学習開始と3回の事前予測比較は別々の条件とする。

# 配置探索の詳細

## 候補期間の列挙

基本期間を[L,R]、全体幅をW=R−L+1、追加可能日数をE=floor(1.5W)−Wとする。期間なしの家事は拡張せず、表示も日付のみ。期間ありでは、まず基本期間、次に追加日数e=1〜Eの順に、前へa日・後ろへe−a日広げた候補を列挙する。aはceil(e/2)、floor(e/2)、ceil(e/2)+1、floor(e/2)−1…の順に0〜eの重複を除いて使う。これで近い前側、同距離の後ろ側、その次の前側・後ろ側を試し、非対称な期間も上限内で検査できる。

その中心で候補がなければ中心を−1、＋1、−2、＋2…へ動かし、各中心で基本幅から上の列挙をやり直す。移動限界はfloor(1.2W)日。候補期間の組(L,R)は重複検査しない。最初に条件を満たした期間を採り、その期間内で日を比較する。前側に適合候補があるのに、後側の負荷が少し小さいことだけを理由に探索順を逆転しない。

期間なしの通常家事はW=1、移動限界1日で前・後を試せる。ただし毎日設定の家事は自動移動せず、日数型の次回おすすめ日は直前の有効完了日より後に限定する。既存予定の再配置では今日・明日の移動元・移動先を除外する。現在日より前へ新規推薦せず、期限切れカードは元の日付を保持する。日付経過だけで探索を繰り返さない。

## 日別の適合と負荷

許可された家事可能時間帯から、登録予定と確定家事予約を引く。同じ予定のアプリ内・Google同期コピーは元IDで統合し、重複区間は和集合として一度だけ控除する。再配置中の家事自身の旧予約だけを外し、他の家事は残す。日跨ぎは実時刻上の連続性を保ち、23:50〜翌0:20を30分枠として扱う。表示日は開始日、時間の集計は各日へ配分する。終日・空き扱い・取消予定の既存の意味を保ち、今日の候補から現在時刻以前を除く。

負荷分散は、配置後の実作業時間÷その日の設定上限時間を第一比較値、重い家事件数、普通の家事件数、全家事件数を続く比較値とする。時間上限0はその日の実施不可、上限未設定なら許可時間帯の合計分数を分母にする。軽い家事に新しい件数上限は設けないが、正の実作業時間と全件数に含める。次に重い家事の休日を優先し、基準日距離、既存おすすめ日、早い日付で決める。

複数家事は、実行可能候補が少ないもの、重いもの、実作業時間が長いもの、安定した家事IDの順に配置する。実行可能な候補ではおすすめ日と確保できた連続時間だけを予約し、期間全日に同じ負荷を重ねない。全候補が不可なら所定のフォールバック日へ置くが、空いていない時間帯に架空の予約を作らない。時刻は未予約のまま、その日の実作業時間・件数を日別負荷に一度だけ計上し、候補不足を隠さない。毎日設定の家事は日付固定ルールを優先する。当日完了した家事は消化済みの実作業時間・件数として一度計上し、新規追加の初回配置でも使う。未完了予約と完了済み負荷を二重計上しない。新しいエラー解消操作は要求しない。

共有家事は自分担当と未担当のものを自分の予定負荷に参照する。未担当分は各人の計算で考慮するが共有回自体を複製しない。他人担当が確定した分は自分の負荷から外す。予約解除は既存の誰か1人・全員等の完了規則に従い、自分が実施した分だけ当日の消化済み負荷へ計上する。他人の完了を自分の消化済み負荷にしない。共通周期・期間・担当指定は個人配置で変更しない。

## 初回の偏りと再配置

初回の仮基準日と同点分散は、利用者ID・家事ID・初回配置版による固定シードで決め、同じ入力で日を変えない。候補日の負荷を比較し、軽い家事も全件今日へ集中させない。短周期の初回候補は探索期間内の将来負荷を仮計上して比較できるが、仮の実カードや完了履歴は作らない。全候補不適合時だけ初回仮基準日へ配置する。

予定変更では区間の開始・終了・空き扱いを含む署名を比較する。日別の合計時間が同じでも時間帯が動けば再計算する。再計算対象の連結成分と入力版を固定し、計算中に完了・設定・予定の新版が来たら古い結果を破棄して最新からやり直す。新旧結果が同じなら書き換えない。天気取得の遅い応答で新しい完了を巻き戻さない。

# 季節と天気を使う範囲

## 季節の切り替え

衣替えなど季節の切り替えが目的の家事は、地域と作業種別ごとの固定日表を使う。日数周期の入力、完了日＋周期、履歴学習、モード倍率、通常の期間拡張・中心移動は適用しない。冬物収納・夏物収納など作業の意味を区別し、年中使う機器へ季節性を作らない。

季節固定型は固定日をおすすめ日として表示する。旧「5月15日・10月15日±30日から選び通常幅を表示する」処理は採用しない。固定日に通常周期から期間幅を付けず、日々の天気・負荷・休日によって日付を動かさない。ほかの通常家事の配置は固定日の季節家事負荷を参照する。

季節回の不変IDは家事ID・作業種別・年・季節回で構成し、地域を含めない。地域・採用日付・日付表版は変更可能な版付き属性として分離する。完了は不変の予定回IDに結び付け、地域変更や日付表更新で完了済み回を再生成しない。実施日から翌年の日付をずらさず、春の回を8月に完了しても秋の別作業を完了扱いにしない。同じ作業の未完了回を重複して積み上げず、完了後は実施日より後にある次の同種固定日へ進む。意味の異なる季節作業を勝手に削除・一括完了しない。

地域別固定日の根拠は、気象庁の気候資料に限定せず、地域別の衣替え時期を明示するメディア情報も使う。対象年、作業の意味、地域範囲、出典、確認日を保持する。記事の表現や画像を転載せず、時期を独自の日付表へ整理する。「中旬」等から特定日にする判断を出典が指定した日と混同しない。地域専用の根拠が弱い場合は、下表で明示した広域代替初期値を使い、媒体がその地域の最適日を公表したとは扱わない。

日付表はアプリ同梱・サーバー配信で同じ形式を使う。初版の更新処理では、完了済み回と今日・明日の回を保護する。それ以外の未完了の将来回は、日付表・地域設定が変わったときに同じ作業・年・季節回を保ったまま再評価する。過去日へ新規移動せず、同じ回を重複生成しない。今日・明日の保護は本人の直接変更以外で解除しない。配信失敗では保存済み表を継続使用し、日付を動かさない。地域未設定・判定不能の初期値は5月15日と10月15日とする。これは地域最適値ではなく従来案からの代替値で、追加の住所入力やGPS許可を要求しない。

## 天気の扱い

METの短期予報は数か月後の季節や衣替え日を予測する材料にしない。天気は、季節固定型以外の洗濯・屋外作業など、実際に天気が関係する通常家事の近い候補だけに使う。学習周期を天気で変更しない。

衣替えは地域別固定日で扱い、短期予報から自動判定しない。通常家事のうち洗濯・天日干し・屋外作業を伴うものだけ、既存の適合条件と実際に取得できた予報項目で候補を比較する。取得できない項目を推測で補わない。雨だけで固定日の季節家事を移動させない。

METから得られない降水確率は欠測とし、0％に置き換えない。降水量・対象時間幅・天気記号など実際に存在する項目で評価する。1時間・6時間・12時間の降水量を重複加算せず、候補作業時間を覆う最細粒度の重複しない区間を使う。予報が欠ける時間は天気適合未判定とし、家事自体を配置不能にしない。

# MET Norwayのサーバー配信

## 構成と利用条件

アプリからMETへ個別アクセスせず、使用中の地域ごとにサーバーが取得・保存し、全端末が同じ地域キャッシュを読む。1日1回は「アプリ全体で1回」ではなく「使用中の地域ごとに通常24時間1回」とする。利用者数に比例して同じ地域を取り直さない。

[MET利用条件](https://docs.api.met.no/doc/TermsOfService.html)と[データのライセンス](https://www.met.no/en/free-meteorological-data/Licensing-and-crediting)に従う。[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)は商用利用を認めるが、出典とライセンスの表示、加工した場合の説明が必要。画面の天気部分または常設の出典欄に「Weather data: MET Norway · CC BY 4.0」を置き、集計・丸めをしている場合は併記する。

LocationforecastはAPIキーを前提としないが、サーバーのUser-Agentにアプリ名と運営者の連絡先を設定する。アプリ全体の20リクエスト毎秒の制約をサーバー方式が免除するわけではない。更新を時刻分散し、Expiresを守り、Last-Modifiedに基づくIf-Modified-Sinceを使う。仕様は[Locationforecast HowTO](https://api.met.no/doc/locationforecast/HowTO)を基準にする。

## キャッシュと更新

- キーは地域ID・代表緯度経度・スキーマ版。既存の地域設定を使い、精密な常時位置や家事履歴をMETへ送らない。

- 地域ごとに24時間間隔とし、地域IDのハッシュで実行時刻を分散する。Expiresより前には再要求しない。

- 初めて使う地域は同一キーの要求を一本化し、取得キューへ入れる。7日間参照のない地域は定期取得を止め、次の参照で再開する。

- 全体の初期制限は毎秒2件、同時処理4件。通常の取得も再試行も同じ制限を通す。これはMETの義務値ではなく余裕を持たせた運用初期値。

- 保存するのは予報本体、取得日時、確認日時、予報生成日時、Expires、Last-Modified、返された予報範囲、変換版。304では予報本体と生成日時を変えず確認日時を更新する。

- タイムアウト15秒。通信失敗と5xxは5分・30分・2時間後に揺らぎ付きで再試行し、その後は次の通常更新へ回す。429はRetry-Afterを優先、403は同じ要求の自動反復を止め運営者へ通知する。

- 端末はアプリ起動・既存更新機会にサーバーの版を確認し、変更分だけ取得する。表示のたびにMETの取得を起動しない。

確認から36時間または予報生成から48時間を超えたデータは新たな天気再配置に使わない。古い天気は取得時刻を示して72時間まで表示できるが、それ以降は天気表示を省略する。取得失敗・失効・欠測だけを理由に既存の家事予定を動かしたり消したりしない。別の正当な配置契機や新規生成があるときだけ天気条件を外して計算する。MET返却範囲外を晴れ扱いしない。時間値は運用初期値であり精度保証ではない。

日本向け全球予報は1日に複数回更新されるため、1日1回取得は負荷削減と鮮度の交換条件になる。数時間先の雨の追従や災害判断を保証する用途にはしない。予報範囲は[データモデル](https://api.met.no/doc/locationforecast/datamodel)と実応答を見て扱い、固定の10日保証を置かない。API料金が無料でも自前サーバー・保存・通信費が無料とは限らず、SLAも自動的には付かない。

## 既存天気処理との接続

現行のOpen-Meteo天気取得を、サーバーを読むプロバイダーへ差し替える。METにない確率項目を必須にする契約は改め、存在する観測項目と欠測を表現できる型にする。地域検索もOpen-Meteo依存が残るため、天気取得だけ変えて商用条件を解決したことにしない。

地域検索の代替は、既存地域IDを維持した日本の自治体・代表座標の静的データを優先する。GeoNamesは[商用利用可能なCC BYデータ](https://www.geonames.org/about.html)として候補にするが、データ品質・地名照合・出典を確認してから採用する。これは将来の実装案であり、外部へ地域データをアップロードした、アカウントを作った、契約を締結したという意味ではない。METへ代表座標は送信され、自前サーバーには端末アクセスのIP等が届くため「位置情報が一切送られない」と表示しない。

# データ構造と処理順序

## 保存する状態

- ChorePolicy：個人通常・共有・ごみ表示・季節固定の種別、モードごとの定期型／必要時型、数値がある場合の家事別初期周期と版、個別固定と明示設定、個別期間幅・休日優先、負荷・実作業分数、季節作業種別、学習区間ID。季節固定・必要時型には通常周期の入力を要求せず、初期周期がないことを0日で表さない。

- CompletionEvent：操作ID、完了ID、家事ID、予定回ID、実施日、UTC日時、タイムゾーン、個人か共有かの由来、表示期間版、当時の初期周期・モード、取消対象ID。

- ModelState：採用方式、丸め前パラメータ、交互位相または暦の予定回、更新前代表周期、比較区間ID、モード変換基底。

- ForecastRecord：予測時点、予定回、モデル候補とパラメータ版、配置前の予測日、実際の採用方式の予測日、評価対象完了ID、誤差、比較区間ID。

- RoundPlan：元の基準日、基本期間、配置後の基準日、表示期間、おすすめ日と予約区間、入力版、公開版。基本期間と表示期間を別に持ち、説明文は不要。

- PlacementInput：同一予定を統合した実時間区間、曜日・日付別勤務休日、家事可能時間帯と日別上限、未完了予約・当日の消化済み負荷・共有負荷、天気版。季節日付表は地域・対象年・作業種別・固定日・出典・確認日・版を持つ。

利用者の追加入力なしで、設定・通常完了・既存予定・確定した家事データから埋める。旧開発データの移行対応は不要。新しい家事一覧の工程や必要時手入れをすべて独立周期家事に変換しない。実作業時間・種別・3モード値等の未定義は開発時に検出し、0分や架空値を補完したり利用者に入力を要求したりしない。

## 完了トランザクション

1. 操作IDの再送と同一予定回の二重完了を排除し、対象回・表示期間版・有効完了の同日集約を確認する。

2. 原本を保存し、新しい有効完了単位の場合だけ更新前代表周期から参照数を一度選ぶ。同日追加原本で学習・採点・交互位相を重複進行しない。

3. その完了より前に作った予測を採点する。無効な比較区間へ成績を混ぜない。

4. 固定・共有・季節固定・必要時型・ごみ表示を学習から外す。個人通常の定期型は期間内なら確定状態維持、期間外または期間なしなら有効3間隔以降で更新する。

5. 候補モデルを再学習し、同時に次回の事前予測を保存する。暦の予定回または交互位相は完了に応じて進める。

6. 対象の未完了回を閉じ、次回計画を新規作成する。当日完了負荷を一度残す。関係家事の再配置にも毎日固定・今日明日保護・季節固定を適用し、空いた当日翌日へ他の日の家事を自動補充しない。

7. 履歴・状態・予定・同期用の送信待ち記録を一つのトランザクションで確定する。失敗時は部分確定しない。

## 2026-11-08 共有家事の日付指定

共有の家事設定の「日付の設定」から、日数周期と毎月の同日指定を切り替える。毎月の場合は開始日に選んだ日を月ごとに繰り返し、31日などがない月だけ月末とする。翌月以降の指定日は元の日を維持する。日数周期と区別して署名付き設定に保存し、共通の家事回・完了と取消し・担当交代・次回検索・依存する家事の参照にも同じ計算を使う。変更前の家事回・実績は書き換えない。毎月指定から日数周期へ戻す場合は、変更時点までに発生した最後の予定日を起点とする。

グループ家事には、管理者が休日優先を選ぶ欄を置かない。各ユーザーの休日と負荷・個人予定から、その人向けの推奨日を実施期間内で選ぶ。幅が0日ならその日を使い、個人の休日設定を共有の正式な日付へ書き戻さない。個人家事の休日優先の選択は維持する。

毎月設定の使用には共有計算draft-55を必要とし、旧版グループでは更新前の毎月設定の書き込みを拒否する。個人向け推奨計算の変更は独立したpersonal-4として管理する。

## 取消と同期

取消は対象完了IDへの補償イベントとし、再送は一度だけ処理する。その完了以前のチェックポイントから対象を除いた後続完了・設定変更を順番に再生し、無関係な変更や後の明示設定を消さない。新設計では完了・取消・モード・固定・有効無効の変更を、順序付きで同一トランザクションに記録する。

取消対象に依存する次回計画・学習・予測成績を無効化して再計算する。3間隔で初めて学習した完了を取り消して2間隔へ戻った場合も、その学習の影響を戻す。取消した記録から得た周期を維持する特例はない。再生予測を過去の事前実績へ加えず、生きている完了と後続設定を保持する。同日原本が残る場合は最初の有効原本から集約単位を再評価する。関連家事の再配置にも今日明日保護を適用する。

完了と取消、設定、予定更新には家事単位の順序と版を持たせる。古い非同期計算の結果は現在の版に一致しなければ破棄する。既存共有同期を利用し、この設計だけを理由に個人履歴の新しいクラウド送信を追加しない。

# 実装対象と開発用データ

LiFlowは開発中で利用者はいない。既存の開発用データは破棄可能で、旧スキーマからの救済・移行・後方互換性・旧家事IDの対応表は作らない。これは無関係な既存機能を削除する指示ではない。実装開始時は対象の最新ブランチを確認し、本書と既存の全面カレンダー同期・共有機能を接続する。

1. 新設計の初期化から必要な状態を記録する。画面の履歴表示を短くしても、家事が存在する間の学習・取消に必要な原本やチェックポイントを消さない。過去1か月で原本を削除する処理を、そのまま新学習へ使わない。

2. 新しい家事データは内部ID・作業範囲・種別・モード別初期値・時間・負荷を明示する。内部IDは実装上の識別子であり利用者に入力させない。旧36件と家事一覧81行の機械的対応は不要。工程・使用後・必要時・表示専用を勝手に通常周期へ変換しない。

3. 完了実施日と対象予定日を分け、共有由来を明示して個人周期学習から除外する。同一回の重複完了と同日有効単位をテストする。

# 検証とリリース条件

- 日数境界：7・8・13・14・29・30・59・60・89・90・179・180日の期間幅、30・31・90・91日の参照数、0.5の丸め、1日未満の最小値を固定テストにする。

- 学習：初期14日でも[60,60,60]から60日を採れる。[14,14,180]の中央値は14日。14日から60日へ変わる履歴で、中央値の段階的な切り替えと指数平均の追従を比較する。滑らかな変化や最適精度を無条件に保証しない。

- モード：固定20日は不変。固定解除は初期値。日数型のモード往復、平年・うるう年、1月31日からの暦月加算、完了を挟まない元規則復元を検証する。

- 初回：短周期は1周期以内、30日超は30日内の探索を先行、混雑時だけ1周期へ拡張。軽い家事を全件今日へ置かず、同じ入力で再配置結果が変わらない。

- 季節：地域別固定日を使い、周期入力・学習・倍率・通常拡張を通さない。遅い完了で別季節の作業を完了しない。天気障害で動かさず、日付表更新時も完了済み・今日明日を保護する。その他の将来回は同じ不変の回IDで再評価する。春の衣替えを完了後に地域を変更しても、地域属性の版だけが変わり、その年の春の回を未完了で復活させない。未完了回の地域変更でも過去日への新規移動と重複生成を防ぐ。

- 期間版：拡張後の期間内完了ではモデルを維持。完了と予定再配置の競合、オフライン完了、旧版欠落でも後付けの期間で勝手に学習しない。

- 探索：基本9〜11日、最大4日で12日だけ空くなら9〜12日を採れる。中心移動時は基本幅へ戻す。全候補不可なら元の9〜11日へ戻し、探索が必ず終わる。

- 時間：連続30分は可、10分の空き3つは不可。重複予定の二重控除、同じ合計時間での時間帯移動、日跨ぎ・夏時間・現在時刻の扱いを検証する。

- 再配置：関係集合だけを一括処理し、負荷を二重計上しない。原位置フォールバックも負荷に残る。古い天気・カレンダー応答が新しい完了や設定を上書きしない。

- 共有：担当済みと未担当の負荷を各人へ正しく反映し、共通周期・共通期間は変えない。共有由来履歴を個人学習に入れず、再送で二重完了にしない。

- 比較：期間内なら勝者が出ても切替禁止。3回中2勝、改善20％かつ0.5日ちょうどは合格。同点・誤差0は維持。4間隔未満で交互型を採らず、モード変更前成績を後へ混ぜない。

- 取消：完了A、設定変更B、完了Cの後にAを取り消してもBとCを消さない。取り消した完了に依存する成績を無効化し、再生予測を過去の実績として採点しない。

- 初期化：旧開発データの移行試験は不要。新しい初期状態と、今日明日保護・個別設定・共有・季節固定を全経路で検証する。天気の304・429・403・欠測・古い予報・地域初回取得を試験し、失敗だけでは既存予定が不動であることを確認する。

- 処理量：モデル更新は該当家事の最大8間隔を中心にし、原本全走査を通常表示から外す。確定カタログ件数・5年相当履歴・1万予定区間などを試験入力として実端末で計測する。家事一覧81行を独立家事81件と決めつけない。これらは性能測定済みの値ではない。

生活群別の予測誤差に加え、観測年数、学習開始率、採点できた予測数、未評価の次回予測、変化前後の成績、予定移動数、禁止操作数、実端末処理時間を報告する。合成ケース・独立模型の結果は実利用者の精度やアプリ合格を証明しない。無効化中の通常完了等を除いた状態遷移が成立する入力で試し、開発用と評価用を分離する。3間隔未満の長周期家事に推定を無理に追加せず、初期周期と既存個別設定を使う。
