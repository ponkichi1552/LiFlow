# 通信・サーバー保存の最小化

2026-11-15の利用者の指示に基づく改修。目的は、端末とサーバーの通信を必要最小限にすることと、サーバーに残す情報を必要最低限にすることの2点。

## 実装前の変更案

- 変更なしの10分タイマーを外す。端末内の変更、サーバーの変更通知、起動・復帰、明示的更新、未完了の再試行を契機にする。認証・契約・天気の期限確認と、Google側だけの変更検知は別の条件として扱う。
- AIの結果は、端末が検証・永続保存した後の受領確認で削除する。HTTP応答を送れただけでは削除しない。入力PDFは処理確定後に削除し、結果を受け取れない場合にも再試行で再解析・再課金しない。
- 共有・本人端末間の配送は変更した項目を暗号化して送り、対象端末への保存確認後に配送用コピーを削除する。未受信のまま期限を迎えた端末は、サーバーに残した全件バックアップではなく、最新データを持つ承認端末から再同期する。
- 配送本文・解析の一時入力と結果は、ログ・永続バックアップへ複写しない。本人識別、承認端末、所属、公開鍵、同期世代・受領位置、二重課金防止と契約確認の最小情報は分離する。
- 保持期限の初期設計値は24時間。これはコード側の上限であり、稼働済みデータを無確認で消す移行操作の許可ではない。

## 自己評価と保護条件

- 通信回数を減らすために変更の取り込みを失ってはいけない。Googleの外部変更を端末内の変更通知だけで知れるとは扱わず、起動・復帰・利用者の更新時に必要な差分を確認する。
- 送信元と受信先の保存済みデータ、未送信の操作、競合候補、権限・署名・因果関係、課金の受付判断を維持する。削除対象はサーバーの配送用コピーであり、端末の家事・履歴・PDFを一括削除する変更ではない。
- 受領確認は対象の利用者・端末・世代・配送内容に結び付ける。他人の確認、古い確認、途中保存、偽装された確認で削除しない。複数件はまとめて確認する。
- 期限切れ後の再同期は、端末内の未送信操作を保全して検証済みの状態に合流する。提供できる端末が不在なら待機し、空データで上書きしない。
- 古いアプリ・既存グループを壊さない互換性の切替を用意する。受信・復旧経路が未対応の状態で履歴の削除だけを有効化しない。
- 自前サーバーでの削除とOpenAIなどの提供元側の保持は別。提供元の即時完全削除を、この実装だけで保証しない。

## 検証する結果

- 無変更・前景待機では固定10分タイマーに起因する同期HTTPを発生させない。
- ローカル変更、遠隔の変更通知、前景復帰、明示更新、通信失敗後の再試行では必要な変更が届く。
- 端末保存前の終了ではサーバーの結果を消さず、保存後の確認・確認応答の紛失・再送でも欠損や二重課金がない。
- 配送対象の確認完了または期限で本文が消え、除名済み・別アカウント・古い世代への再配送をしない。
- 新規端末・期限切れ端末の再同期と同時編集で、端末内の未送信内容や履歴を失わない。

実装・検証の結果と、稼働環境への配備・移行は区別して記録する。

## 実装した通信条件

| 経路 | 通信の契機 | 無変更時 |
| --- | --- | --- |
| 共有・本人端末間 | 起動・復帰、端末の変更、遠隔の変更通知、明示更新 | 固定10分同期を廃止。未完了・失敗分のみ期限とバックオフで再試行 |
| 端末の参加承認待ち | 承認情報の変更通知 | 固定5秒の問い合わせを廃止 |
| 個人Google Calendar | 起動・復帰、表示範囲の拡張、ローカル変更、明示更新 | 健全な状態を固定タイマーで取り直さない |
| OSバックグラウンド | ローカルDBにある未送信・未完了・失敗状態 | 同期済みのTasks・Calendar・共有は通信せずスキップ |
| AI結果の受領 | 解析中の進捗照会と完了結果、端末保存後の受領確認 | 端末の同一PDF解析キャッシュを利用。保留中の受領確認は次の解析操作で再送 |

Google Tasksの正常時の24時間再照合条件、Googleの認証・利用制限、契約期限、天気キャッシュの有効期限は別の判断であり、無効化していない。Firestoreの変更監視接続や認証更新に必要な通信は残る。「無変更なら通信パケットが常に0」という意味ではない。

共有は署名付きの変更操作を送る。本人設定は既存の競合検出を保つため、変更があったときに1つの小さな設定レコードを原子的に送る。本人の空き時間は本文を含まない暗号化済みキャッシュ単位で更新する。初期接続・鍵更新・期限切れからの再取得では必要なスナップショットも送る。全データを毎回アップロードする方式ではなく、すべてを文字単位の差分に変えたという意味でもない。

## 受領・期限・削除

### AI解析

端末は結果ハッシュを検証し、PDFと結果をローカルSQLiteへ同一トランザクションで保存してから `POST /api/appliance-care/jobs/{jobId}/receipt` を送る。確認画面への反映をネットワーク上の削除完了まで待たせない。保存失敗なら受領確認を送らず、応答紛失時も保存済み結果・同一受付IDから再開する。

受領確認はFirebaseの本人認証、受付所有者、結果ダイジェスト、有効期限、ランダムな受領トークンを照合する。確認だけのために追加課金・契約・ネイティブ証明を要求せず、課金APIの認証条件は緩めない。確認済みジョブは結果本文や入力manifestを持たない小さな再送防止レコードへ置換する。

同じ説明書の通常参照は端末キャッシュを使う。利用者が明示的に再解析した場合は最新結果へ置き換え、次の通常参照で以前の結果へ戻さない。端末の時計が戻っても保存日時だけで過去の解析を優先しない。

入力PDFの分割本文は処理確定時に削除する。結果本文は正しい受領確認時に削除する。未受領の結果・入力は24時間で取得期限を迎え、既存の定期清掃または解析ワーカーの清掃で実体を消す。これは24時間ぴったりの物理削除を約束する設定ではない。受付・課金判断・クォータ用のハッシュと数値は、本文と分離して既存の課金整合性を維持する。

### 共有・本人端末間

サーバーの暗号化された配送本文は、対象の承認端末すべての永続保存確認、または作成から24時間で削除対象になる。既存の署名検証・権限・競合処理は維持する。本人用の設定本文を削除しても、前後の版を比較するためのカーソルとハッシュは残す。

期限切れや新規端末は承認済み端末へ必要な範囲の再配送を要求する。元の署名・暗号・所有者のmanifest・サーバーの独立した受付証跡で検証し、端末の未送信編集や競合候補を維持する。提供端末が不在なら待機し、空の設定で置換しない。

再配送は最大10操作のページ、分割本文は最大16MiBに制限する。応答の親レコードを先に作成し、分割送信完了後に準備完了へ切り替える。受信端末が保存後に要求を閉じると、Rulesが遅れて到着する本文の追加を拒否し、削除ワーカーが子孫も含めて消す。要求の親だけをTTLで削除して断片を残す方式は使わない。

削除ワーカーは本文ではなく必要なメタデータと受領状態を監視し、削除判定の読み取りも必要なフィールドに限定する。大きな暗号化本文でFirestoreのトランザクション上限を超えないよう、共有本文は1回に最大10レコードを処理し、残りは続けて消す。未公開スナップショットの送信途中の断片も期限対象にする。待機中の固定ポーリングは行わず、実際の変更、次の未処理期限、失敗後の再接続だけで動く。監視が失敗した場合は30秒から最大5分のバックオフで接続し直し、停止後には再接続しない。

## サーバーに残す情報

| 残す情報 | 必要な理由 |
| --- | --- |
| UID・所属・承認端末・所有権・公開鍵・鍵配送用の暗号封筒 | 本人と送信先を認証し、除名・鍵更新・端末承認を守る |
| 同期世代・受領位置・版・ハッシュ・最小の署名付きmanifest | 再送、巻き戻し、偽の再配送、競合の誤判定を防ぐ |
| 操作のサーバー受付証跡 | 再配送した操作が本当に受け付けられたものか独立して検証する |
| AI受付・課金・利用量・契約検証の最小レコード | 二重課金、消して再実行するクォータ回避、失効後の不正受付を防ぐ |

家事・予定・履歴の本文、本人の設定本文・空き時間キャッシュ、共有PDFの分割本文、AI入力PDF・結果本文は配送・処理用の期限付きデータとする。端末上のデータは引き続き保持する。外部のGoogleアカウントに利用者が同期した情報を削除する変更ではない。

## 配備と既存データの切替

この作業はローカル実装と隔離した検査まで。稼働中のRules、API、削除ワーカー、端末アプリは配備しておらず、既存のサーバーデータは削除していない。既定の `EXPO_PUBLIC_SHARING_EPHEMERAL_DELIVERY=0` では新しい共有本文の削除は始まらない。無変更の固定同期を外す変更はこのフラグから独立している。

1. 対応する `firestore.rules` と `firestore.indexes.json` を同じ環境へ配備し、当該アカウント・除名・世代更新の拒否条件を確認する。
2. APIと解析ワーカーを同じ版へ更新する。AIの受領確認は旧版アプリからは届かないため、その場合は24時間の期限と清掃で削除する。
3. 同じFirestoreへ接続する管理用プロセスで `npm --prefix server/appliance-care-api run delivery:work` を起動する。既存のFirebase Admin用の認証を使い、認証情報や本文をログに出さない。
4. 一時配送フラグを有効にしたアプリを全承認端末へ渡す。端末が復旧用の暗号化済みデータをローカル保存して準備完了を広告するまで、ワーカーは削除を有効化しない。クライアントが自らワーカーのactiveを有効化することもRulesで拒否する。
5. 準備後に、実環境でも2端末の永続保存→受領→本文削除→期限切れ端末の復帰を確認して切り替える。旧版へ戻す場合は本文の取得互換性がないため、削除開始後の単純なアプリのダウングレードを避ける。

削除ワーカーは既存のFirestoreを利用するサーバープロセスであり、Firestoreを自前DBへ置き換える作業ではない。FirestoreのPITR・バックアップ、プロキシや監視製品の本文ログ、OSバックアップなどの保存設定は別途点検が必要。OpenAIの `store:false` は設定済みだが、提供元側の保持方針まで自前サーバーの削除で変更できない。

AIは合成PDFと合成結果を使った。実際のOpenAI送信は利用者の指定どおり保留している。実環境でのデータ削除・配備・バックアップ設定変更は行っていない。今回はUI変更がなく、追加のシミュレーター起動や実機への上書きは行っていない。
