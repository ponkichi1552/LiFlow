# Google同期の中断・複数端末検査

2026年11月5日。変更箇所の初回検査と、その後の確認を記録する。現行v13の全体検査は3,294件、隔離Cloudは142件が通過した。両OSそれぞれの通常Tasks同期とAndroid個人Calendarの実サービス往復も確認した。同一アカウントの2実機同時作成と現行版の自然な背景同期は未完了で、iPhoneの追加操作は利用者の指示で後回しにしている。

## Tasksの受信

個人用・V2用の実際の保存ポートに、アカウントとGoogleリストごとのSQLite受信キャッシュを接続した。スキーマ26は既存の家事・設定・履歴・Google対応表を変更せず、受信用の3テーブルを追加する。

初回は100件ずつ取得し、各ページと次の取得位置を同じトランザクションで保存する。途中の一覧で完了取り込みや削除判定を始めない。再起動後は保存した位置から続け、全ページが揃った時点で確定キャッシュを置き換える。

以後は`updatedMin`で差分を取得し、未変更の行を保持する。非表示の完了と削除も取得対象に含める。境界には最初の応答のGoogle側時刻から5秒の重複幅を設け、端末の時計を送信する境界として信用しない。応答に時刻がなければ次回も全件取得する。[Google公式tasks.list](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks/list)

7日経過時と端末時計を過去へ修正した場合は全件を再確認する。期限切れ・反復したページ位置は確定キャッシュを保ったまま再取得へ戻す。壊れた受信メタデータは該当アカウント・リストのキャッシュだけ再構築する。作成意図・個人履歴・共有履歴をキャッシュの復旧対象に含めない。

合成データ1万件では初回100リクエスト、変更2件の次回は1リクエストとなり、保存済みの未変更9,998行への更新は0件だった。これはNode SQLiteと模擬HTTPによる測定であり、端末の起動時間や実Google通信の測定ではない。受信済みキャッシュ全体を照合用に読むCPU・メモリー費用は残る。

## 時間枠と作成意図

通常・完了直後・OS workerは15秒、明示した長い手動実行は最大100秒の共通予算を使う。既存の待機列、認証取得、複数ページ、JSON・multipart本文の取得を含む。native側がAbortSignalを無視しても呼び出しは時間切れとして戻り、遅い応答から追加ページ・遅いOAuth・予定再生成を始めない。

実行中の後処理が終わるまでは同じ同期を登録したままにし、時間切れを新しい並行実行の許可にしない。SQLiteの進行中トランザクションそのものを強制中断する仕組みではない。未送信の変更と既に確定したページは残し、OSによる次回起動は保証しない。

送信前の予算・認証検査で止めた要求には、アプリ内部で「HTTP未開始」を記録する。この場合だけ未送信の作成予約を解除できる。送信開始後のタイムアウト、5xx、応答消失は成功した可能性があるため解除しない。後続のローカル予約失敗で、同じ未送信チャンクの先行予約が取り残される経路も修正した。

端末が独立したSQLiteを持つ同時作成の重複防止（R66）、実Google Tasksの条件付きDELETEの挙動（R20/Q05）は、このキャッシュ・予算検査で証明した範囲に含めない。

## Calendarの取得完了と初回保存

個人の自動配置では、表示要求の範囲を「受信完了」の証明に使わない。取得対象の全カレンダーのカーソル、未受信ページ、未処理Inbox、繰り返し展開の完了と実際の範囲を照合する。初回・未取得・不完全な多カレンダー受信を、primaryだけのFreeBusyが0分だから空いているとは扱わない。

確認済みの全予定がある場合は実時刻の和集合を使う。個人予定10–11時とGoogle予定10時30分–12時、同じ同期コピーを合わせても10–12時の120分となる。鮮度を保ったまま取得日時だけが変わっても自動配置の入力版を変えず、実際に鮮度が切れた場合は判定を更新する。

カレンダー初回読み込みが終わる前でも、初期分類の予定を保存できる。存在しない初期分類だけを保存トランザクション内で作り、変更済みの分類や存在しないカスタム分類を勝手に補完しない。

## 共有予定のGoogle出力

別端末が正常に版2を送信済みで、自分には版1のETagしかない状態から、最新の版3へ進める検査を追加した。Google本文が、同じグループの署名・権限・サーバー受付を検証済みの過去の系列版と一致する場合だけ、新しいETagを使える。マーカー文字列だけでは認めない。

再送信の新しいETagと本文も、HTTP前に端末内の送信意図へ保存する。応答消失後はその正確な意図を回収する。古い未確定送信より新しい正規版が既にGoogleにある場合は、古い本文を書き戻さずに受付を回収する。検査中に共有の最新版が変わった場合は、古い画面の本文を送らず次回へ回す。

Googleだけで編集された未知の本文、未知の版、系列の証拠では確認できない個別回は保留する。他の独立した予定の更新は続ける。この保留を上書き・復元する新しい確認UIは追加していない。個別回の過去版の証明と、手動削除・任意編集後の解消方法は残課題として区別する。

## 追加：削除の条件をHTTPへ渡す

削除APIは最新GETの強いETagを必須とし、正確な `If-Match` を送る。欠落・弱いETag・ワイルドカード・改行付きの値ではHTTPを開始しない。削除までの間に変更され412が返った場合は対応表を保持し、別の不要予定の処理は継続する。模擬HTTPと実照合ロジックの45件、明示プローブの隔離検査2件がPASS。

Google Tasksの[性能ガイド](https://developers.google.com/workspace/tasks/performance)にはETagを使った条件付きPATCHの説明があるが、例は汎用APIであり、[tasks.delete仕様](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks/delete)には条件付きDELETEの明示的保証がない。そのため、今回の模擬412検査を実Googleでの保証へ読み替えない。

`tests/native/google-tasks/conditional-delete-probe.mjs` に、認可済みトークンをメモリーで受け取る明示実行用の実サービス検査を用意した。新しく作った一意な名前の合成リストだけを使い、完了後に古いETagのDELETEを送信して、412・完了保持・最新ETagでの削除を個別に確認する。自動テストから実サービスを呼ばず、トークン・予定内容・応答本文をログへ出さない。片付け前にも合成リストのIDと名前を再検査し、不確かな場合は削除しない。その後、Androidの既存権限を端末内だけで使うnativeプローブで、R20/Q05の412・完了保持・最新ETagでの204・合成リストの後片付けを実測した。[実測記録](google-tasks-cross-device-2026-11-05.md)。
