# MET地域キャッシュと自治体検索の実装・検証

採用済みの2026年11月4日仕様を実装した。ローカル・隔離Firestoreでの確認と、実サービスでの動作確認を区別する。その後に行った実MET取得とGoogle Cloudへの配備は末尾に記録した。端末内の確認が済んだ範囲は、クラウドでの確認と区別する。

## 地域検索と既存データ

地域検索は通信を行わない静的索引へ変更した。旧Open-Meteoの予報クライアント・地域検索クライアントは削除した。かな・カナ・ローマ字・都道府県を含む入力を端末内で検索する。検索索引の文字正規化は最初の検索まで遅延し、起動時に全地域の検索処理を行わない。

元データは[Geolonia住所データ](https://geolonia.github.io/japanese-addresses/)の2026年11月5日取得分。公開CSVのSHA-256は `d8f14da1c1ff15f1118452eb0c334d3d8fc45f9df3ccf08fc176ba5856eb2689`、51,860,404 bytes、277,630行。欠測している町丁目の座標441行を補完せず除外し、全1,894市区町村に実データの代表点が残ることを検査した。政令市単位の20候補を派生し、計1,914地域を格納する。

市区町村ごとに、町丁目代表点の平均に最も近い実在の代表点を選び、小数4桁に丸めた。これは市役所所在地や利用者の現在位置ではない。旧座標の照合用に、元の町丁目代表点の外接矩形も保持する。外接矩形を行政界のポリゴンとは扱わない。生成スクリプトは元CSVのハッシュを検査し、未確認の最新版を自動採用しない。

生成物は `server/appliance-care-api/src/weather/municipalities-data.json`。SHA-256は `9fde6e50d80b0f6f30c29ffb0e6fc8b1ef3ef987cb2f8efac1d2b80b9ab672f5`。モバイルとサーバーが同じデータを参照する。元CSVは外部ストレージの `LiFlow-development-cache/weather-sources/2026-11-05/` にコピー・SHA-256照合して保管し、一時ダウンロードを削除した。個人データ・認証情報は含まない。

SQLite 26→27は追加移行。地域ID列と公開予報の破棄可能なキャッシュ表だけを追加する。履歴・家事設定を削除しない。以前の設定には元の地域検索IDが保存されていなかったため、存在しない旧IDの互換性を主張しない。旧設定は、自治体名・都道府県の完全一致が一意で、旧座標が元データの範囲と丸め許容差内にある場合だけ対応付ける。曖昧な自由文字列は推測しない。

都道府県と、鹿児島県が公表する[奄美12市町村](https://www.pref.kagoshima.jp/aa02/chiiki/oshima/soshiki/kannai.html)の対応から、既存の季節家事の日付表へ接続する。予報から季節日付を推測しない。対応不能時は採用済みの全国代替値を使う。

## 予報の取得とキャッシュ

[METの利用条件](https://api.met.no/doc/TermsOfService)と[Locationforecast HOWTO](https://api.met.no/doc/locationforecast/HowTO)を確認した。アプリはMETを直接呼ばない。地域IDを指定してLiFlow側の公開予報キャッシュを読み、初回要求は保管先の取得待ちへ登録する。画面表示のたびに外部予報を取り直さない。

通常取得は地域ごとに約24時間間隔（キー由来の±30分の分散）で、Expiresより前に再取得しない。7日間参照のない地域は定期取得を止め、再参照で再開する。同じ地域の初回要求は集約する。Firestore上の共通ゲートにより、別プロセスを含め毎秒2件の開始・4件の取得受付を制限する。再試行も同じゲートを通す。ゲート閉鎖時は同じ拒否トランザクションを地域数分繰り返さない。

取得は有限の独立worker jobで行う。HTTP応答を返した後のCPU実行や、モバイルのBackground Pushの短い枠には依存しない。タイムアウトは15秒。通信が中断を無視しても呼び出しは終了し、遅い応答は保存しない。未終了のtransportの受付枠は直ちに解放しない。異常終了したworkerからの復旧には60秒のleaseを使う。古いleaseの応答は、新しいworkerの保存を上書きできない。

通信失敗・5xxは5分、30分、2時間の揺らぎ付き再試行後に通常周期へ戻る。429はRetry-Afterを優先し、共通の待機期限にも反映する。403は自動反復を止め、保管先に停止状態を保存し運営用ログを出す。既存の予報を破棄しない。予期しないredirectは、無制限の追加HTTPや別ホストへの接続を避けるため自動追跡しない。

Last-ModifiedをそのままIf-Modified-Sinceへ渡す。304は本体・生成日時・取得日時を保持し、確認日時などのメタデータだけを更新する。生応答は512KiB以下、変換後の時間区間数も制限する。単位・日時・順序・測定値・欠測を検証する。保管先はクライアントから直接読取・更新できないRules境界に置く。

端末は選択中の地域だけを既存の更新機会に確認し、ETag一致時は本文を受け取らない。保存済みの予報を即利用し、更新待ちは初期表示を止めない。HTTPが遅く返っても、別の完了・設定変更・日付変更などで古くなった画面の計算結果を保存しない。

## 配置計算

METのUTC区間を実際の候補作業時間へ照合する。1・6・12時間の降水量から最細粒度の重複しない完全被覆を選び、同じ時間の降水量を二重加算しない。短い作業だからといって粗い降水量を比率で割り、架空の値を作らない。降水確率がない場合はnullを保持し、実際にある降水量・記号で判定する。時間の穴は不明として扱い、配置不能とはしない。

通常の洗濯・天日干し・屋外作業の意味を持つ家事だけを対象にする。洗濯機フィルターなどの設備清掃は、名前の部分一致で洗濯と誤判定しない。室内干し指定、季節家事、毎日固定、今日・明日・過去の保護対象には既存の保護を適用する。配置用の内部予約区間は、利用者へ開始時刻入力を強いるものではない。

確認から36時間／生成から48時間を超える予報は新規の天気配置に使わない。表示可能期間は72時間まで。失効・取得失敗・欠測だけでは既存の家事を移動・削除しない。別の正当な配置契機と新しい家事回では、使えない天気条件を外す。メタデータだけの更新でモデルを学習し直したり、予定回を再生成したりしない。天気と配置の保存が途中で失敗した場合は同じSQLiteトランザクションで戻す。

## 検証と残作業

- 自治体・旧設定照合・SQLite移行・季節接続6件PASS。
- METの欠測・時間区間・鮮度・再試行・HTTP制限・タイムアウト等の単体検査13件PASS。
- 関連する予報・地域検索・個人配置・互換ポリシーの限定検査70件PASSの後、追加・変更箇所を個別に再検査。これをアプリ全件の合格とは扱わない。
- 設定の天気項目と、初期設定を含む出典リンクの操作検査2件PASS。
- 隔離Firestoreで、複数worker・再起動・lease更新・端末からの読取／改変拒否を検査。公開サービスそのものへの攻撃・負荷試験は行わない。
- Expo SDK58でiOS／AndroidのMetroバンドル生成成功。サーバー専用のキャッシュ管理・User-Agent設定・workerがモバイルへ混入していないことを確認。これは実端末の実行や起動速度の合格ではない。

配備前に運営者の実際の連絡先を含む `MET_WEATHER_USER_AGENT` を設定する。連絡先を作り話で補ったり、利用者のGoogleログイン用メールを無断で流用したりしない。未設定時はMET取得を停止する。`EXPO_PUBLIC_WEATHER_API_URL`、または既存の `EXPO_PUBLIC_APPLIANCE_CARE_API_URL` のHTTPS保管先をアプリに設定し、`npm run weather:work` の定期jobとFirestore index設定を準備する。APIキーをアプリへ置かない。

本番配備・実予報・実端末での最終確認、個人設定／共有負荷を含む配置計算全体の最終検査は未完了。設定されたCloud基盤の費用・HTTP入口の制限・worker起動条件は配備先で別途検証する。無料APIを使うことを保存・通信の無費用保証とは扱わない。


## 既存Google Cloudへの配備と実測（同日追加）

所有者が既存プロジェクトへの請求先登録を完了し、APIでbillingEnabledを確認した。天気用のStandard Firestore `liflow-weather`を同じ東京リージョンへ追加し、サービスIDのデータ権限はそのDBだけへ条件付けた。デフォルトDBの家事・認証・同期データにはアクセスできない。新規サービスアカウントにJSON秘密鍵は作っていない。名前付きDBは無料枠の対象ではなく、保存・読取・通信は課金対象になり得る。

Cloud Run `liflow-weather`は公開予報のGETとhealthだけを扱う。家電AI・購入・ユーザーデータのURLはマウントしない。共通ハンドラを既存APIとも共有し、同時要求を集約、予報応答は30秒、取得待ちは5秒の上限付きプロセスキャッシュでまとめる。鮮度の境界と時計の逆戻りを再検査し、失敗した応答はキャッシュしない。入口のレート制限は偽造Forwardedヘッダーを信用しない。最大1インスタンス、最小0。これは費用の絶対上限やDDoS防御の保証ではない。

別のCloud Run `liflow-weather-worker`はIAMで非公開とし、Cloud Schedulerの専用IDだけに起動権限を与えた。1分ごとのリクエストが最大32件の有限処理の完了を待ってから返る。応答後のCPUには依存しない。空のCloud Run Jobを毎分起こして最低課金時間を重ねる構成は避けた。各地域の24時間周期・全worker共通の取得ゲート・失敗時の待機を維持する。最大1インスタンス・同時1リクエスト・最小0。既存のCLI用有限workerも同じ処理を使う。

本番と同じruntime IDを使った検査専用Cloud Run実行は、名前付き天気DBの作成・読取・検査分だけの削除に成功し、デフォルトDBの存在しない検査パスへの読取はPermission Deniedだった。`weather_iam_boundary`の成功ログとexecution完了を照合した。検査専用jobは削除した。家事の文書は読んでいない。天気DBのRulesは全mobileアクセス拒否。配備後の既存デフォルトRulesのSHA256は `1db27c3788a01bf0c8c3880fdbc05bbdb01a95f01ddd34db5768361198c22f51` のままだった。

公開URLは `https://liflow-weather-db3dkwyp3q-an.a.run.app`。HTTPSでhealth200・既存予報200・同じETagで304・未知地域404・書込405・AI用URL404・未認証worker403を実測した。実際のモバイル用ProviderもこのHTTPS応答を解析し、224時間区間を保持して同一地域の連続要求を1回へまとめた。Mac上でのProvider確認を両実機の天気検査へ読み替えない。

最初にMacからMETへ1回の取得を行い、200／224区間を確認した。その予報と制御値はハッシュ照合して専用DBへコピーし、Expires前に再取得しなかった。新規地域13104はクラウドからの取得でHTTPエラーとなり、所定の再試行を保持している。失敗を成功とせず、予報を持たない地域は202のまま。固定コードとHTTP statusだけの診断を追加し、応答本文や連絡先をログへ出さない。
