# 共有Google Tasksの端末間同時作成

R66の修正。対象は同じLiFlow利用者・共有グループ・Googleアカウント・既存保存先リストを使う独立した端末。個人のGoogle接続や共有家事の権限を変更しない。

## 方式

新規POSTの前に、既存Firebaseの本人専用パス`privateGoogleTaskClaims/{uid}/occurrences/{hash}`で作成許可を原子的に確保する。100件のHTTPチャンクごとに、SQLiteの保存とFirestoreの予約をまとめる。1件ごとに全共有履歴の検査やネットワーク往復を繰り返さない。未設定・停止中のGoogle連携や通常の画面表示ではこの保管先を初期化しない。

クラウドに保存するのはスコープ・家事回・Google Task IDのハッシュ、試行ID、状態、版、サーバー受付時刻。元のアカウントID、GoogleリストID、Google Task ID、家事名、予定日、固定マーカー、OAuthトークンを保存しない。グループメンバーにも公開しない。作成記録は家事の完了・承認を許可する証拠にはならず、実際の保存は従来の権限検査を通る。

一方が確保した家事回を他端末はPOSTしない。次の同期でGoogle上の固定マーカーに一致する1件を採用し、同じTask IDへ収束する。

## 中断と失敗

予約の期限切れや端末停止だけでは再POSTを許可しない。応答が不明な操作を保持する。明確に送信していない場合やHTTPの確定した拒否では、その試行だけを解放できる。削除に伴う再作成も、対応するTask IDの記録に一致する場合だけを解放する。新たな確認画面は追加しない。

旧版が既に作った複数候補は無条件に削除しない。固定マーカーは削除の認証証拠ではない。異なるTask IDを勝手に上書きせず、既存の曖昧な対応は保留する。Googleの実DELETEがIf-Matchを強制するかはQ05として別に検証する。

## 検証

- `tasks-global-claim-area-final.log`:関連64件PASS。実SQLiteの100件保存・最終フェンスでの全件rollback、明確な拒否後の再送、Cloud応答喪失の保持、ネイティブ配線、既存の完了・取り消し・期日更新を含む。
- `tasks-global-claim-cloud-final.log`:隔離Firestore6件PASS。実際の独立した本人端末鍵とSQLite DB、同じ空のGoogle一覧を再現し、新規作成が1組だけになり、次回の両端末のTask IDが一致した。Google自体は合成APIであり、実サービスの実測ではない。
- 他UIDの読取・書込、本人でも一覧取得・削除、不正な版・状態・時刻・平文追加を拒否。100件予約・解放は対象試行だけへ適用。呼出後の入力変更、時間切れの遅いtransaction、受付応答喪失を検査した。
- `tasks-claims-paid-cloud-final.log`:追加後の隔離Firestore7件PASS。利用権がない・期限切れ・別人の利用権では読取・予約・解放を拒否し、猶予期間は既存の予約を保ったまま利用できることを確認した。

既存の本番Rulesがmainの元ファイルと一致することを読取で確認し、戻せる元ソースを保存した。2026-11-05に本人専用の新しいパスだけを追加して適用し、公開後のRulesが検査済みソースと完全一致することを再取得で確認した。SHA256は`1db27c3788a01bf0c8c3880fdbc05bbdb01a95f01ddd34db5768361198c22f51`。このRules適用では他のCloud設定や既存データは変更していない。通常Releaseへ組み込み、両OS別々のGoogle接続で通常同期を確認したが、R66の同一利用者・同一リストへの2実機同時作成は未完了。


## Q05・R20の実Google確認

2026-11-05、Android10の実機と既存のGoogle Tasks権限で条件付きDELETEを実測した。唯一の検査専用リストに作った1件を、GET後に完了へ変え、古いETagでDELETEすると412だった。再GETで完了状態が残り、新しいETagでのDELETEは204。自分の検査リスト名とIDの一致を端末内で確かめ、そのリストだけを後片付けできた。`tasks-conditional-live-android-v7.log`。

トークン・アカウント識別子・Googleの応答本文は端末外へ出していない。検査は同一署名の別APKから既存のSDK保存と権限を使い、React側の通常処理を開始しない独立したprovider検査である。補助APKだけを削除し、LiFlow本体とデータは保持した。これはR20の削除前提を裏付けるが、R66の両実機同時作成や通常同期の成功を意味しない。通常画面で接続した共有Tasksの最初の同期はretryとなっており、別途調べている。


## 実機で見つけた初回タイムアウトへの追加修正

実機の通常接続は初回にtimeoutとなり、private接続状態はretryPending、保存先未作成・リンク0件のままだった。ログにはトークン・Googleの生ID・家事名を出さず、端末内の読取専用検査で状態だけを照合した。

調査で、HTTP前後に使う接続状態・private受信キャッシュ・作成予約・ID対応の記録まで、共有業務履歴を再演算する `readCurrent` を呼んでいた。既存の `withPrivateStorage` へ接続し直し、現在の本人・端末・所属・roster・DB結合と保存後の再照合を保ち、同じ業務履歴の再演算を外した。予定の抽出・完了取込・完了ACKは従来の認証済み業務状態を使う。privateの表初期化は最初のtransactionが確定してから準備済みにし、その後のHTTP guardでDDLを繰り返さない。

さらにv2の共通coordinatorへ同じ処理予算を渡し、Google操作の待ち行列で期限が切れた仕事が、あとから本人入力の準備・認証を開始しないようにした。関連33件PASS、追加の保存途中失効rollback検査もPASS。

通常Release v10のAndroid実機で、同じ接続の「共有家事を今すぐ同期」を実行した。画面は追加24件・更新0件・完了と取消の取込0件、最終同期15:07を示した。その後の端末内読取専用照合では、idle・エラーなし・保存先あり・成功記録あり・リンク24件だった。`android-real-tasks-sync-v10-result.log`。過去の検査用DBは停止状態のままで、データの初期化は行っていない。

この結果は通常画面からのAndroid初回同期を確認するもの。iPhoneと同じリストへの同時作成、OS自然実行、同期所要時間は別の確認が必要で、成功へ読み替えない。

## iPhone通常Releaseの接続と同期

通常Release v12を699入力のハッシュ・全260ファイル・署名を照合して上書きした。データを保持したまま、実XCTestで設定から共有Tasksへ移動し、既存アカウントを確認した。その同じ表示中の本人識別情報を照合してから接続し、追加24件・更新0件・完了と取消の取込0件、最終同期11/5 16:05、連携中を確認した。`tasks-v12-ios-connect.log`と`tasks-v12-ios-sync-result.json`。テスト全体の27.355秒は同期だけの所要時間ではない。

最初の画面検査は、展開中の設定項目の端にあったボタンを押した後、設定に留まり失敗した。外部テスト補助コードが対象全体を画面内へ入れてから押すように修正し、同じアプリで再確認した。元の失敗を保持し、アプリ本体や合格条件を変更していない。

現在のiPhone・AndroidのGoogle接続は別アカウントである。両OSそれぞれの通常同期の成功として扱い、同一利用者・同一Googleリストへの同時作成検査R66や自然な背景同期の成功へ読み替えない。アカウントは差し替えていない。


## 別アカウントへの切り替えで判明した連携状態の不整合

実機でGoogleアカウントを選び直しても、個人用Google Tasksの保存先と対応IDが前のアカウントへ固定され、「以前連携したGoogleアカウントを選択してください」で止まることが分かった。旧IDを別人へ送らない拒否は働いていたが、明示的なアカウント変更が完了しないアプリの欠陥だった。

修正版v18では、明示的な変更時だけ前の個人用連携状態を端末内でアカウント別に保管し、新アカウントの状態へ切り替える。旧アカウントへ戻せば保存先・対応ID・未反映状態を復元する。Google側の予定・タスクや、端末の家事・設定・完了履歴は削除しない。個人Calendarの制御状態も同じトランザクションで切り替え、受信カーソル・未送信編集は元のアカウントへ残す。

SQLiteでの216件の対応IDの往復復元、処理途中の本人変更・期限切れ・破損データによる全体rollback、Googleの旧処理の終了待ち、Settingsの古い非同期結果の拒否を含め、関連201件PASS。最後のSettings修正後も関連38件、lint・型検査・482契約の登録検査PASS。v18は両実機へ既存データを保持して導入済み。iOSは既存の検査済みnative本体にSDK58の新しいRelease JSを組み込み、57個のnativeコード・データ区画と署名を照合した。新規のnative全面ビルド成功を意味しない。実際のアカウント変更と同一利用者の2端末同期は、この時点では検査中である。
