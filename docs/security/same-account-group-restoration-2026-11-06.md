# 同じアカウントでの共有グループ復元

別端末で同じLiFlowアカウントへログインすると、参加済みのグループを自動で復元する。招待リンクや所有者の手動承認は追加しない。異なるアカウントの新規参加は、従来どおり招待と所有者の承認を必要とする。

## 権限と鍵

端末ごとに異なる署名鍵・鍵交換鍵を使う。既に承認されている同じUIDの端末だけが、新しい本人端末へ共有鍵を暗号化して配送できる。既存の所有者、他のメンバー、設定や業務履歴を変更する権限は与えない。1アカウント4端末の既存上限を維持し、除名済みの端末IDは自動で復活させない。

今回の本人端末追加だけは、署名付きの追加マーカーと新しいtransport epochを使い、同じ共有秘密鍵を継続する。メッセージごとのHKDF・nonce・epochの結び付けは維持する。通常の参加、除名、所有者変更、復旧では従来どおり鍵を更新する。新端末は古い所有者Snapshotとその後のイベントから復元し、自分が参加する前の操作を新しく作成する権限は得ない。本人端末を追加した署名者にSnapshotの所有権は与えない。

FirestoreのRulesでは署名を検証できないため、一般メンバーへrootの直接更新を開放しない。既存Google Cloudプロジェクトの専用HTTPSサービスが、端末と同じ公開契約・署名検証コードを読み込み、現在のFirebase UID、失効、利用権、所属、署名付きroster全履歴、要求nonce、配送先、除名履歴、復旧ロックを検証する。その後、本人端末1台の追加だけをtransactionで確定する。家電AIの実行・利用回数とは独立している。

サーバーへ送るのは公開鍵と署名、暗号化された配送鍵、最小限の受付情報だけ。端末秘密鍵、平文の共有鍵、平文の家事、GoogleのOAuthトークンは送らない。FirebaseのIDトークンは認証先HTTPSサービスへだけ送り、リダイレクトしない。ログやエラーには認証情報や応答本文を出さない。

## 再送と保存順序

要求は本人UIDごと4スロット、サーバー受付から15分有効。要求の署名・nonce・最初の信頼pinを端末に保存してから送信する。応答喪失時も同じnonceで照合する。新端末では鍵をSecureStoreへ保存してからグループを有効化し、署名付きACKの後に配送用の暗号文をサーバーから実削除する。期限切れ・retentionで退役した鍵の配送は取得できず、TTLでも後片付けする。

要求・配送文書はモバイルの直接アクセスを拒否する。Rulesで公開するのは同じUIDだけが読める更新シグナル1件。HTTPS側は4件までの取得、本文上限、同時数、短時間のレート、日次上限を設ける。共有・本人の初期画面を待たせず、前景・復帰・既存の単一背景workerから再試行する。アカウントが変わった遅い応答を適用しない。

有効なFirebaseセッションの更新は追加操作なしで利用できる。認証から24時間経過したことだけを理由に再ログインは求めない。IDトークンの期限・失効と、要求のサーバー受付期限は別に検査する。

## 限界

既存の承認端末がすべてオフラインなら、鍵が届くまで自動で待つ。秘密鍵をサーバーへ預けて迂回はしない。既存端末をすべて紛失した場合の鍵復旧は、この機能の成功として扱わない。

新端末の初回bootstrapは、認証済みFirebaseの本人所属と署名付き履歴を信頼してpinを確立する。既存端末は保存済みpinから検証する。Firebase管理基盤の能動的な乗っ取りまで独立した外部信頼点で防ぐ方式ではない。同じFirebaseセッションが盗まれた場合の危険もあり、これは第三者監査済みという意味ではない。
