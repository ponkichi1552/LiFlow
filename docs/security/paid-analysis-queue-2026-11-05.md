# 家電AIの永続受付と実行境界

監査R06の作業記録。未コミットの開発コードと隔離環境の検査であり、公開APIの稼働・正規端末証明・実OpenAI呼び出しの完了を意味しない。家電共有へ追加の確認操作を入れる案は採用しない。

## 修正

公開HTTP APIは、受付ID・利用枠・実行ID・暗号化したアップロード入力を一つのFirestoreトランザクションで保存してから202を返す。応答後のPromiseで解析を起動しない。別のワーカーが保存済みの受付を読み、本人の有効性と契約を再確認してから処理する。APIキー・IDトークンを受付へ保存しない。

新規受付では、端末がPDFと製品情報をHPKE（X25519、HKDF-SHA256、AES-256-GCM）で暗号化する。受付APIは、暗号文を変更せず480 KiB以下に分割して保存する。受付IDと公開ヘッダーを認証付き暗号の追加データに含め、別の利用者や受付へ移した暗号文を拒否する。ヘッダーには公開鍵の識別子、一時公開鍵、利用者ごとの重複防止用ハッシュ、再解析フラグを含める。PDFと製品情報を復号できる鍵は解析ワーカーだけに設定する。 [HPKEの仕様](https://www.rfc-editor.org/rfc/rfc9180.html)

6 MiBのPDFは暗号ヘッダーと暗号化した製品情報を加えたバイナリで受付へ1回送る。旧JSON送信の約8 MiBから約2 MiB減る。データと結果の大きなフィールドは索引から除外する。結果は一つのフィールドで段階保存・最終確定する。Firestoreのdocument上限は1 MiB、トランザクションの要求上限は10 MiB。 [Firebase公式上限](https://firebase.google.com/docs/firestore/quotas)

状態は、受付待ち、入力準備、解析開始、結果保存済み、確定済みで区別する。入力準備の30秒leaseは更新できるが、解析開始の確定後は別ワーカーによる有料呼び出しを許可しない。開始確定と外部呼び出しの間で停止した場合も、費用発生の不明な操作を再実行しない。10分の受付期限を過ぎたものは中断として扱う。

ワーカーは復号後にPDFの形式・ページ数を検査する。新方式で有料開始前に拒否・期限切れとなったときは、暫定確保した月間枠を返す。開始後は、OpenAIから結果を得られなかったとサーバーが期限内に記録した場合に月間枠を返す。結果保存後の停止では結果の確定だけを再試行する。日次の全体受付数には記録する。

保存失敗の監視イベントは受付IDと段階だけを記録する。説明書・製品名・認証情報・上流エラー全文をログへ出さない。PDF chunksは最終確定と同じトランザクションで削除する。期限を過ぎた未処理入力も既存のサーバー側pruneの対象にする。サーバー停止中まで厳密な時刻削除を保証するものではない。

## 配置前に必要なこと

`npm --prefix server/appliance-care-api run analysis:work` はHTTP応答から独立した単発ジョブ用の入口。受付期限内に定期起動される基盤が必要。HTTP APIから起動したり、リクエストベース課金の応答後CPUへ依存させない。[Cloud Runの背景処理に関する公式説明](https://docs.cloud.google.com/run/docs/tips/general#background_activity)

独立ワーカーの稼働確認が90秒以内にあり、受付に使われた鍵をそのワーカーが読めるときに、新しい利用枠を予約する。既存の受付・保存済みの結果は引き続き確認できる。ワーカーは実行中30秒ごとにも稼働確認を更新する。

定期ジョブは期限切れ入力も削除する。取得時に結果やPDFを読み込まず、削除用の期限フィールドだけを取得し、バッチ上限内で処理する。Firebaseの有料TTL削除は今回有効化しない。

端末には `EXPO_PUBLIC_APPLIANCE_CARE_UPLOAD_KEY` として32バイトのX25519公開鍵を小文字16進数で設定する。公開HTTP APIには対応する公開鍵のSHA-256を `APPLIANCE_CARE_UPLOAD_KEY_IDS` に設定する。ワーカーには `APPLIANCE_CARE_UPLOAD_PRIVATE_KEYS` として32バイトのX25519秘密鍵を小文字16進数のJSON配列で設定し、OpenAIの鍵もワーカー側に置く。1つの構成で最大4世代の鍵を扱える。

鍵を更新するときは、先にワーカーへ新旧の秘密鍵を設定し、稼働確認を取る。次に受付APIで新しい識別子を許可し、アプリの公開鍵を更新する。旧アプリを受け付ける期間と既存受付の処理が終わってから、古い識別子と秘密鍵を外す。旧キュー形式を読む間は `APPLIANCE_CARE_QUEUE_KEYS` と `APPLIANCE_CARE_QUEUE_ACTIVE_KEY_ID` をワーカーだけに残す。

## 検査

暗号化を含む変更箇所の67件、Firestore実SDKの14件がPASS。最大PDF・700KiB近い結果・二重起動・停止地点・旧claim・別の本人／受付・tag／nonce／digest改ざん・鍵世代変更・キー未設定を検査した。実OpenAIは呼んでいない。暗号化追加前に全3,048件とCloud131件も通過したが、以後は利用者の指定に従い変更箇所だけを検査し、最終全件検査は作業完了時に行う。

公開AIの有効化には、正規端末・再インストール保護の実装と検証、公開環境での鍵設定、ワーカーの配置と稼働確認が必要。
