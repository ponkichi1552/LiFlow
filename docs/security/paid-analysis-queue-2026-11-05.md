# 家電AIの永続受付と実行境界

監査R06の作業記録。未コミットの開発コードと隔離環境の検査であり、公開APIの稼働・正規端末証明・実OpenAI呼び出しの完了を意味しない。家電共有へ追加の確認操作を入れる案は採用しない。

## 修正

公開HTTP APIは、受付ID・利用枠・実行ID・暗号化したアップロード入力を一つのFirestoreトランザクションで保存してから202を返す。応答後のPromiseで解析を起動しない。別のワーカーが保存済みの受付を読み、本人の有効性と契約を再確認してから処理する。APIキー・IDトークンを受付へ保存しない。

PDFと製品情報はNode.js標準のAES-256-GCMで認証付き暗号化し、480KiB以下のbinary chunksで保存する。nonceはCSPRNGの12バイト、tagは16バイト。本人・受付ID・入力digest・版とサイズをAADへ結び付け、別の利用者や受付への暗号文移し替えを拒否する。復号結果はtag検証後にだけ解析へ渡す。専用のサーバー鍵はFirestore・端末・ログに保存しない。グループの端末間暗号化とは別の、解析サービス側の一時入力保護である。[Node.jsの認証付き暗号API](https://nodejs.org/docs/latest-v24.x/api/crypto.html#class-decipheriv)

6MiBのPDFを含むJSONはおよそ8MiBで、二重のBase64にはせず、暗号文をbinaryで書く。データと結果の大きなフィールドは索引から除外する。結果は一つのフィールドで段階保存・最終確定し、同じ700KiBの結果を同一documentへ二重保存しない。Firestoreのdocument上限は1MiB、API要求上限は10MiB。[Firebase公式上限](https://firebase.google.com/docs/firestore/quotas)

状態は、受付待ち、入力準備、解析開始、結果保存済み、確定済みで区別する。入力準備の30秒leaseは更新できるが、解析開始の確定後は別ワーカーによる有料呼び出しを許可しない。開始確定と外部呼び出しの間で停止した場合も、費用発生の不明な操作を再実行しない。10分の受付期限を過ぎたものは中断として扱う。

OpenAIから結果を得られなかったと内部で分類できた結果だけ、既存方針どおり月間枠を戻す。その結果を期限内に保存できていれば、枠の確定が遅れても保存済みの受付時刻で判定する。結果保存後の停止では結果の確定だけ再試行し、解析を繰り返さない。日次のサービス全体受付上限は戻さない。

保存失敗の監視イベントは受付IDと段階だけを記録する。説明書・製品名・認証情報・上流エラー全文をログへ出さない。PDF chunksは最終確定と同じトランザクションで削除する。期限を過ぎた未処理入力も既存のサーバー側pruneの対象にする。サーバー停止中まで厳密な時刻削除を保証するものではない。

## 配置前に必要なこと

`npm --prefix server/appliance-care-api run analysis:work` はHTTP応答から独立した単発ジョブ用の入口。受付期限内に定期起動される基盤が必要。HTTP APIから起動したり、リクエストベース課金の応答後CPUへ依存させない。[Cloud Runの背景処理に関する公式説明](https://docs.cloud.google.com/run/docs/tips/general#background_activity)

独立ワーカーのheartbeatが90秒以内にない場合、新しい受付は利用枠を予約する前に拒否する。既存の受付・保存済みの結果は引き続き確認できる。ワーカーは実行中30秒ごとにもheartbeatを更新する。構成ファイルだけを置いてワーカー未配置のまま有料受付を始める経路を作らない。

定期ジョブは期限切れ入力も削除する。取得時に結果やPDFを読み込まず、削除用の期限フィールドだけを取得し、バッチ上限内で処理する。Firebaseの有料TTL削除は今回有効化しない。

API・ワーカー共通のSecret設定は`APPLIANCE_CARE_QUEUE_KEYS`（鍵IDから32バイト鍵の正規Base64へのJSON）と`APPLIANCE_CARE_QUEUE_ACTIVE_KEY_ID`。上限4世代で、先に全読み手へ新鍵を配布し、その後に暗号化のactive鍵を変える。未処理の受付が終わるまで旧鍵を残す。未設定・不正な設定・必要な旧鍵の欠落を平文保存へフォールバックさせない。公開基盤への本物の鍵の作成・登録は今回行っていない。

## 検査

暗号化を含む変更箇所の67件、Firestore実SDKの14件がPASS。最大PDF・700KiB近い結果・二重起動・停止地点・旧claim・別の本人／受付・tag／nonce／digest改ざん・鍵世代変更・キー未設定を検査した。実OpenAIは呼んでいない。暗号化追加前に全3,048件とCloud131件も通過したが、以後は利用者の指定に従い変更箇所だけを検査し、最終全件検査は作業完了時に行う。

現行の公開AIは正規端末・再インストール保護の準備が不足しているため、従来どおり停止を維持する。今回、課金基盤の有効化・クラウドへの配置・実PDFのアップロード・有料解析は行っていない。ワーカーの実配置と稼働監視、失敗後の運用手順、最終の全件再検査は公開条件として残る。
