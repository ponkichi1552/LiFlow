# LiFlowのサーバー通信と保存量

2026年11月20日、6.2-astraの3担当で、実行中のサービス、端末の同期、一時配送と復旧を監査した。本番のCloud SchedulerとFirestore Rulesは読み取りで確認した。通信回数の一部は、現行コードをインメモリの検証環境で実行して数えた。

## 現在の構成

家事の計画、カレンダーの表示、復号、ローカル通知は端末で処理する。GoogleカレンダーとTasksへの連携も、端末からGoogleへつなぐ経路が中心。共有と本人同期はFirestoreを直接使う。自前サーバーで既存のNodeサービスを動かした場合も、アプリからFirebase AuthとFirestoreへの接続は発生する。[共有の接続先](../../src/platform/sharing/firebase-services.ts)・[配送ワーカー](../../server/account-device-api/src/sharing-delivery-main.mjs)

本番の天気ワーカーは1分周期で有効。待ちが空でも候補照会が1回ある。METへの通常の予報取得は、利用中の地域ごとに約24時間に1回。初回の地域登録と取得失敗時の再試行も同じワーカーが処理する。[天気ワーカー](../../server/appliance-care-api/src/weather/firebase-runtime.mjs)・[地域別の取得条件](../../server/appliance-care-api/src/weather/regional-store.mjs)・[Firestoreの読み取り料金](https://firebase.google.com/docs/firestore/pricing#minimum_charge_for_queries)

## 今回の修正

- 天気の更新候補を探す照会は地域IDのみ取得する。参照時刻や実行権だけを更新する場合は、保存済み予報をFirestoreへ再送しない。
- 共有の最新位置に到達済みなら空の履歴照会を省く。本人同期の承認履歴にも同じ早期終了を入れ、現在のサーバー位置と照合した結果で判断する。
- 参加承認を待つ端末は、自分が読める招待と申請だけを監視する。承認・拒否・取り消し・期限切れで同期を起こし、拒否後に同じ監視を登録し続ける経路を外した。
- 本人端末の復元APIは、申請の固定4枠を1件ずつ取得する方式から、実在する枠をIDで絞る照会へ変更した。権限の照合後に問い合わせ、結果を枠の順序で返す。
- PDF解析の完了トランザクションで、入力断片と再読込用メタデータを消去する。新方式の受領処理から同じ断片への削除操作が発生しない。未更新の完了済みレコードも受領できる。
- 検索条件に使っていない復旧用の暗号本文、署名付き目録、承認履歴JSONのFirestore単一フィールド索引を除外した。

関連の単体テスト178件、Firestoreエミュレーターでの天気・PDF、端末復元・本人同期・署名付き配送、招待承認・共有同期を確認した。lint、型検査、機能契約と共有スケジューラーの版検査も通過した。

## 効果が大きい次の変更

1. **天気の毎分起動**。地域別の次回時刻を永続化して、その時刻と新規登録で起動する。自前環境では、最早時刻まで待機するワーカーをAPIから起こす構成にできる。日次の照合は再起動や通知紛失の穴埋めに使う。固定時刻を日次にするだけでは、24時間に最大30分のずれが足されて翌日の枠を逃し、更新間隔が約48時間になる地域がある。初回、再試行、期限を過ぎたリース、上限32件の継続を検証してから起動周期を切り替える。
2. **無変更同期**。改修前の模擬結果はグループ3読取、空の履歴検索2回、受領確認の読取1回。空の検索を省く修正に加え、同一同期で最初に読んだ最新位置の再利用と、同じ受領位置の再確認を減らす余地がある。
3. **端末復元と本人データ**。端末復元の通知には連番があり、その連番と処理待ちの有無でAPIを呼ぶ条件を絞れる。個人カレンダーは内容が同じ場合も180日分を再暗号化・再公開する経路がある。鮮度を別の署名付き情報で更新し、本文の署名、世代、参照可能な期間を照合できれば、本文は再利用できる。
4. **復旧時の転送**。現行の共有操作は暗号文のオブジェクトと同じ値のJSON文字列をどちらも梱包する。64 KiBの模擬暗号文1件では、圧縮前の転送データが263,836バイトから132,198バイトになる余地があった。旧端末が読める形式を残し、送信担当不在時の交代、受信側の既存署名と受付証跡の照合を検証する。
5. **家電の解析受付**。受付済みのジョブを再開する際、端末からPDFを再送する経路がある。6 MiBのPDFなら1回の再送で約8 MiBのJSONになる。端末に受付IDを永続化し、同じ本人と入力の再開は結果取得だけにする。受付応答を失った場合の処理1回保証は維持する。公開家電APIと解析ワーカーの直近配備記録は未配備。
6. **変更通知とアップロード**。共有操作のたびに、変更位置とともに署名付き名簿も端末へ転送される。通知を位置・世代・ダイジェストに絞り、名簿は世代が変わったときに照合できる。自前配送APIでは、複数の変更を1回にまとめ、書込み確定時に操作ごとの受付証跡を返せる。

## 自前サーバーに置く最小限の情報

端末の認可に使うアカウント識別子、所属、公開鍵と世代、操作の順序と再送防止、端末ごとの署名付き受領位置を保持する。配送用の暗号文は短期保存領域に置き、受信端末が保存を完了したと確認してから消去する。期限後に復帰した端末は、別の承認端末からデータを受け取る。復旧可能な端末が見つかるまでは、唯一のコピーを保全する。自前移行時は、短期領域の暗号文を永続バックアップや本文ログへ複製する経路も点検する。[署名付き配送の削除条件](../security/signed-device-delivery.md)

Firestoreを外すには、既存の直接接続を認可された配送APIと変更通知へ移す。移行先の署名は移行先の登録に結び付ける。家電PDF解析を有効にする場合は、OpenAIへの送信と課金管理を共有配送から独立させる。

## ラズパイでの予備計測

Raspberry Pi 3 Model B Rev 1.2の実機は64ビットDebian 13で、利用可能メモリ744 MiBと空き容量3.4 GiBを確認した。公式のARM64版Node.js 24.22.3を一時領域で起動し、SHA-256とSQLiteの動作を確認した。テストファイルとNodeの一時コピーは検証後に片付けた。[Node.jsの配布元](https://nodejs.org/en/blog/release/v24.22.3/)

microSD上で合成データの保存・2端末の受領・本文削除を各サイズ100件実施した。1件あたり3回の永続SQLiteコミットを行い、本文が空になり受領2件が残ることを確認した。4 KiBは中央値30.87 ms、95パーセンタイル1,180.13 ms。64 KiBは中央値21.73 ms、95パーセンタイル64.18 ms。実行したPythonプロセスの最大メモリは13.4 MiB。アプリからの通信、署名検証、同時接続を含む実サービスの速度は別途計測が必要。microSDの遅い書き込みが出たため、配送実装では中央値に加えて遅い側の待ち時間を測る。

本番の署名付き配送用Rulesを配備し、共有4件と本人同期2件の配送先で、削除を無効にしたまま受領署名の収集を開始した。初回集計に続く読み取りでは、承認登録9件中1件の共有端末で、保存を示す署名と最新位置の一致を確認した。全承認端末の署名の一致と実機間の期限切れ復旧がそろうまで、削除ワーカーは停止した状態で運用する。

## 追加計測と改修

- 本番の天気ワーカーログを直近24時間分読み取った。成功1,440回のうち1,439回が取得対象ゼロで、取得試行は1件だった。これはログの件数で、課金額の実測とは区別する。
- MacでFirestoreの各操作に5 msを入れた合成試験を旧版と交互に13回実行した。取得待ち3地域から同じ2件を取得した場合、候補照会3回→1回、取得制御の事前照会3回→1回、制御を伴うトランザクション5回→4回。中央値は64.35 ms→31.63 ms。METの304では既存の予報本文を転送せず、確認日時と版だけを更新する。
- 変更を送信しなかった共有同期では、受信後の同じ確認を繰り返さない。同期完了時には端末の保存位置を確認して受領を送る。署名済みの配送位置が同じ場合、再署名も省く。
- 共有の受領済み要求32件と各1片を使った検査で、配送素材を削除する際の文書の個別読取は384件→291件。要求を締め切る検証を1回にまとめ、本文を消す各トランザクションでは権限、復旧ロック、要求の作成時刻を見直す。検索で返る文書はこの数に含めていない。
- PDF解析を受け付けた後は、端末にジョブIDを保存し、再試行は結果取得から再開する。6 MiBの合成PDFの再送相当は約8 MiBのPOST本文。初回の受付応答を失った場合は同じ受付キーを使う。
- 新しく選んだPDFは、送信データへの変換前に端末でサイズ・形式・ページ数を調べる。iOSはPDFKit、Androidは権限を持たない別プロセスでPdfRendererを使う。送信したファイルは、従来どおりHTTPSを経由し、サーバーでも解析前に検査する。解析待ちデータの暗号化には既存のAES-GCMを使う。
- 受付済みのPDFを解析待ちに保存する際、Base64へ変換したものを再度バイト列に戻す処理を省いた。元のバイト列でPDF形式とハッシュを確認する。Macで6 MiBの合成PDFを旧版と交互に15回ずつ処理したところ、キュー入力を暗号化して分割するまでの中央値は23.72 msから15.87 msになった。
- Macで正規の合成署名320件を5回ずつ検証。現在のNoble JavaScript実装は中央値255.53 ms、Node.jsのOpenSSL実装は13.80 ms。検証器単体の比較で、既存の特殊な署名を含む互換性とRaspberry Piのサーバー全体の応答時間は別。採用する署名形式とNode.js実装は既存のものを使う。

## 自前サーバーで起動する天気API

`server/appliance-care-api` で Node.js 24 を使い、`LIFLOW_WEATHER_SQLITE_PATH` に書き込み可能な永続ファイルの絶対パス、`MET_WEATHER_USER_AGENT` に運営者の連絡先入りUser-Agentを指定して `npm run weather:self-host` で起動する。`PORT` の既定は8080で、HTTPはループバックだけで待ち受ける。アプリから使うときはHTTPSで公開する。公開APIのパスと予報の形式は現行と共通。

SQLiteの同じファイルには1プロセスを使う。次回取得、再試行、処理中の予約をSQLiteに保存し、最も早い時刻にだけ起きる。初めて参照された地域は保存するとワーカーを起こす。待ちが空の場合、定期照会・Firestore通信・MET通信は発生しない。Macの回帰検査で24時間の待機、新規地域、再起動後の再試行、途中停止した処理の引き継ぎを確認した。本番の毎分Cloud Schedulerは現行の天気APIに接続中。

Raspberry Pi 3 Model BのmicroSDで同じ再起動・引き継ぎ検査を実行した。METを合成応答に置き換えた計測では、新規8地域の受付が中央値22.30 ms、予報をSQLiteから読めるまでが中央値122.82 ms。8件中最も遅い計測は1,764.46 ms。キャッシュ済みHTTP 304は80回で中央値5.51 ms、95パーセンタイル8.59 ms。キャッシュからの応答中にMETの追加呼び出しはなく、Node.jsのRSSは計測中最大84 MiBだった。外部回線と実際のMET応答時間は含めていない。
