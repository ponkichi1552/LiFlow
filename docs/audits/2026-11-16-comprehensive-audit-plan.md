# 総合検証後の全ページ・サーバー監査

2026-11-16の追加依頼。先に現在の実機検証と見つかった不具合の修正を進め、その後、全ページ・必要機能・最適化・サーバーを対象に1,000件の指摘を洗い出す。サーバーも稼働版と最新コードを照合し、検証・互換性・配備条件を満たして更新する。

## 実施順

1. [実機検証の216候補](../physical-device-validation-2026-11-15.md)の実施結果を、端末・アカウント・バンドル・証拠と対応付ける。未実施、環境待ち、明示保留を通過へ置き換えない。
2. 再現した不具合を修正し、必要な回帰・lint・型検査・実機再確認を行う。正本のmainへ反映し、GitHubの検査を確認する。
3. API・Rules・index・解析ワーカー・配送ワーカー・天気・本人端末承認の稼働構成とソースを調べる。既存版を復元できる状態にして、同じ検証済みの版を配備・照合する。一時配送の切替は全端末の準備と復旧検証の条件に従う。
4. 全ページと状態違いを実画面で見直す。初回、未設定、空、通常、長文、大量、入力中、通信断、失敗、復旧、権限違い、明暗、文字拡大、OS違いを対象にする。
5. ユーザーの目的に沿って、必要な機能が一連の操作で完結するかを検討する。家事の実施、予定変更、個人・共有の切替、家電の説明書、初回設定、検索、通知、認証、オフライン、復旧を往復して確認する。
6. 根拠付きの指摘を台帳へ蓄積し、重複・誤認・既存仕様との矛盾を再確認する。必要性、利用頻度、影響、修正の優先度を整理する。

同日の追加指示により、発見した不具合と最適化箇所は修正・回帰検査まで進める。変更前に原因と影響範囲を確かめ、対応した指摘へ検査結果を結び付ける。実測していない仮説は、確認状態を維持して調査する。

## 指摘の条件

目標は指摘1,000件。検査項目数と指摘数は別に数える。同じ共通部品の原因は一つの指摘へまとめ、影響するページを併記する。確認した不具合、最適化の候補、UI/UXの改善案、不足機能を区別する。

各件には、安定したID、種別、確認状態、対象ページまたはサーバー経路、発生条件、期待と実際、ユーザーへの影響、根拠、優先度、修正案、追加検証を付ける。台帳は1行1レコードのJSONLで管理し、件数を検証する。現時点の計画は1,000件の発見・確認を示すものではない。

UI/UXでは、初見で理解できること、必要な操作が少ないこと、配置の一貫性、視認性、不要な文章・視線移動・処理待ちを抑えることを評価する。既存の使い分けを確かめてから変更を提案する。実装を伴う場合は、依頼内容と変更案を文章化し、仮デザイン・操作の自己評価を含め、2分以上検討してから変更する。

## 実行・情報の保護

検証用アカウントと専用グループを使用する。資格情報、招待URL、秘密鍵、個人予定本文、パケットの送信先を公開台帳へ含めない。パスワードを記録しない。OpenAIの有料実API検査は、利用者の指定による保留を維持する。

API・Rulesの更新と、既存本文の削除や一時配送フラグの有効化は別の操作として検証する。稼働版の確認、互換性、受領・復旧経路、旧端末の準備状況を照合してから切り替える。端末保存済みデータを失う変更、準備条件を省く削除、配備だけを根拠にした成功判定は行わない。
