# 設定ページのデザイン照合

2026年11月9日。作業コピーの main（基準コミット `4bc8b82` と未コミットの改修）を、個人用・参加中グループの2つのiOSシミュレーターで確認した。結果は「全ページが統一済み」ではない。以下の残りを、次の画面調整で扱う。

## 今回反映した変更

1. **本人の誕生日は日付だけにした。** 一般設定で日付を開き、日付選択の「完了」で保存する。名前・メモ・地域・分類・入力の破棄を求める予定編集画面には移動しない。本人分は一つの予定を更新し、他の誕生日や入力途中の予定は消さない。従来登録された名前付き誕生日も、カレンダーに残る。
2. **他の人の誕生日はカレンダーから登録する。** 個人の新しい予定で「誕生日」分類を選ぶと、名前付きの毎年・終日の誕生日になる。家事の時間を塞がない。設定の本人分とは別の予定として保存する。既存予定の分類変更で日時を勝手に変える処理にはしていない。
3. **iOSの時刻ホイールを中央に配置した。** 共通の CalendarField の横幅を引き伸ばさず、ネイティブの測定幅で中央に配置する。時刻・5分刻み・保存先は変更していない。
4. **「手順に見出しを追加」を白系の補助ボタンにした。** 共通の SettingsAction を使い、ページ背景上の通常操作として控えめな枠を付けた。追加処理そのものは変更していない。

## まだ残る不統一

| 箇所 | 確認した差 | 次の調整案 |
| --- | --- | --- |
| 家事追加、共有家事の詳細設定の上ヘッダー | SettingsHeader と異なる手製ヘッダーで、タイトルの太さも異なる。中央配置・戻る操作自体はある。 | 共通ヘッダーへ寄せる。保存待ちを守る戻る処理は保持する。 |
| 全家事の初期化、交代順の操作、収集日の編集中止 | 通常の押せる補助操作なのに、文字だけの表示が残る。交代順には ↑・↓・× がある。 | 通常の補助操作を共通部品へ寄せる。削除と並べ替えの意味を区別する。 |
| Google連携・端末間同期の淡い背景内のボタン | 同じ背景内で白系の枠なしボタンと、枠付きボタンが混在する。 | panel 内の通常操作という共通ルールを適用する。アカウント変更・ログアウトを末尾の独立した操作にする既決事項は維持する。 |
| カレンダーの分類名・RGB値の入力 | 入力欄に背景・枠がなく、編集できる値か判別しにくい。 | 通常の入力欄と同じ背景・入力範囲を付ける。分類色を選んだだけでは保存しない挙動は保持する。 |
| 未接続の表示 | Calendar は本文、Tasks は色付きの小ラベルになっている。 | 同じ意味の接続状態は同じ表現へ寄せる。認証失効・通信エラーとの区別は保つ。 |
| 通知の見出し | 個人家事の通知は太字、共有家事の通知は通常の太さで、同じ階層に見えにくい。 | 同じ階層のラベルとしてそろえる。共有だけの時刻設定は残す。 |
| 天気の「連動を解除」 | 通常操作と同じ色で、解除という意味の色が共通ルールと異なる。 | 他の解除操作と意味を合わせる。 |

分類色の編集枠がライト表示で一度濃く見えた。色の固定値が原因と断定していない。モーダルや表示サイズの変化も含め、再現確認が必要な観測として残す。

誕生日の冗長な入力は今回解消したため、残件として数えない。通常予定の編集・分類色の編集は引き続き独立した調整対象になる。

## 確認範囲

| 入口 | 実画面で開いた内容 |

| 生活リズム | 休日、頻度、件数・時間上限、平日・休日の時間帯、休日カレンダー |

| 共有グループ | 未ログインの入口、ログイン後の参加・作成、参加中のトップ、メンバー・招待、グループ名・ルール、空の申請、同期・復旧の入口 |
| アカウント・連携 | Calendar、個人・共有 Tasks、端末間同期の未設定・設定済み、端末追加入力、アカウント変更・ログアウトの配置 |

ライト・ダークの主要な状態を確認したが、全ページの全状態を両テーマで網羅したという意味ではない。招待の発行、承認・除名、他端末の失効、権限変更、復旧の確定、課金は実行していない。状態が必要な箇所はコードで経路を確認し、実画面の成功として数えていない。Android実機・iPhone実機・外部サイトの画面は今回の確認範囲外。

### 時刻選択の棚卸し

- 平日の開始・終了、休日の開始・終了の4か所をライトで開き、中央配置を確認した。
- カレンダーの開始・終了の2か所をダークで開き、中央配置を確認した。
- 共有予定も同じ CalendarEditor / CalendarField を使うことをソースで確認した。共有保存先の選択状態での時刻ホイールは、独立した実画面検査としては数えない。
- 日付ホイールも、本人の誕生日選択で中央に収まることを確認した。
- 生活リズムで複数の時間帯を設定した場合も、同じ共通部品を繰り返す。追加した全行を別々に開いたわけではない。
- 通知の「時」「分」や日時変更フォームの数値欄は、ホイール型の時刻選択ではない。

## 検証と証拠

- 変更範囲の3ファイルのテスト、**28件成功**。本人の誕生日の更新・重複拒否・削除後の再登録、別の誕生日と下書きの保持、個人DBへの限定、iOSの確定前保存防止、Androidのキャンセル、一般設定の保存、カレンダーからの別人の誕生日登録を含む。
- 日付を回した直後に「完了」を押す条件では、再描画前の古い日付を保存する問題をテストで再現した（`birthday-rapid-before.log`）。選択の最新値を即時保持する修正後、同じ条件も上記28件で通過した。
- lint、型検査、機能契約の登録検査、差分の空白検査を実施。全件テストやCloud攻撃検査を今回のUI照合の成功とはしていない。
- 両シミュレーターへデータを保持して更新。再インストールによる初期化・アンインストールはしていない。既存の署名条件を保持し、更新前後の保存済み Documents のファイル内容を照合した（個人13ファイル、共有16ファイル）。ネイティブの再ビルドはしていない。
- 最終確認時、検査用に切り替えた両シミュレーターの表示設定をライトへ戻した。
- Git commit / push は実施していない。
