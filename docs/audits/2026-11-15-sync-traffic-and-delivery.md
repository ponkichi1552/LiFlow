# 通信量と受信・操作性の追加監査

対象の開始点は `33d1cb3`。前回の最小化を、通信が少ないことだけで合格にせず、必要なデータの到着と通常操作の待ち時間から再評価する。

## 実装前の仮説と変更案

1. 再配送の先頭8件・監視の先頭32件だけでは、未完了の古い要求が残ると後続要求が処理されない。作成日時とIDのカーソルで新規要求をページ取得し、新しい要求の通知を契機に進める。一度送った同じ応答本文は読み直し・再送しない。
2. 再配送の受領確認を受信位置だけでまとめると、同じ位置を持つ別の未受信ファイルまで閉じ得る。要求ごとに、端末の対応する暗号化本文が永続保存済みか確認してから閉じる。確認対象は既知の要求に限定し、全件の再問い合わせを避ける。
3. 他端末への再配送が通常のグループ情報取得・編集を待たせ得る。再配送は同時実行をまとめた独立した処理で進め、画面操作は自分の権限確認・保存だけを待つ。失敗時の再試行とアカウント変更時の拒否は維持する。
4. カレンダーの表示範囲が変わらないまま戻った際に、Google側だけの変更が取り込まれる契機を失っていないか確認する。必要なら画面を開くという実操作で差分確認し、短時間の重複要求をまとめる。無変更の固定タイマーは復活させない。
5. 起動・復帰・同時変更・通信断・受領応答の紛失・期限切れ・大量の分割本文・アカウント変更について、重複送信と到着停止の両方を検査する。
6. AI結果を保存済みでも受領確認の送信に失敗すると、次の解析まで残る。端末の送信待ちがある場合だけ、起動・復帰・ローカルの送信待ち更新・必要な失敗再試行で確認を送る。送信待ちがなければ認証初期化やネットワーク送信をしない。同じDB・アカウント・接続先の処理はまとめ、違うアカウントの処理へ混ぜない。

## 自己評価と合格条件

- 無変更で待機しても業務同期を繰り返さない。同じ要求・同じ本文に対する余分な読み取りや書き込みを避ける。
- 要求数がページ上限を超えても後続が届く。別の本文の受領確認で未受信の要求を閉じない。
- 再配送が遅くても、別の通常操作の読み取り・編集を待たせない。
- 端末の保存失敗・古いアカウント・除名・世代変更・改ざんを、通信削減のために見逃さない。
- Google側の変更を表示するために、アプリ再起動や設定画面の往復を余分に要求しない。
- 実装した条件は修正前に失敗する回帰で再現する。独立したAuth／Firestoreと実SQLiteで受信結果を確認する。
- 稼働中のサーバーのデータは監査用データへ流用しない。実APIの有料解析は引き続き保留し、シミュレーターを増やさない。

追加で、OSの送信待ち判定が実際の未送信変更を見落とさないこと、処理時間の上限を迎えた未実行の連携を成功扱いしないことも合格条件とした。承認・再ログインのような人の操作待ちと、通信失敗・未実行の再試行を分け、正常な別の同期経路まで再実行しない。

## 再現した不具合と修正

| 問題 | 利用者への影響 | 修正 |
| --- | --- | --- |
| 再配送の先頭8件だけを処理し、監視も先頭32件まで | 大量の分割本文や古い要求があると後続が届かない | 作成日時と文書IDのカーソルで全ページを処理。新しい要求の通知では増分だけ取得 |
| 再配送の受領を位置だけでまとめる | 同じ位置の別ファイルまで受信済み扱いになる | 要求の種類・対象・範囲と、対応する端末内の永続保存を確認してから受領。受領対象の全件検索を廃止 |
| 他端末への再配送を通常の読み取りが待つ | 相手側の復旧が遅いと、自分の画面表示まで遅れる | 共有・本人端末間の再配送を通常の読み取りから分離。同じ処理は合流し、アカウント変更後の送信を拒否 |
| 送信元が後から本文を取得しても再配送が起動しない | 別端末にデータがそろっても受信側が待ち続ける | ローカルの本文保存を契機に未完了の既知要求を再開。要求メタデータを取り直さない |
| 同じ範囲のカレンダーへ戻るとGoogle側の変更を確認しない | 再起動などの余分な操作が必要になる | カレンダーを開く実操作で差分確認。30秒以内の連続表示は直近の成功結果を使い、固定周期の照会はしない |
| Googleから取り込んだ変更が新たな同期を呼ぶ | 受信直後に不要な再照会が発生する | ローカル変更の通知では送信待ちを先に確認。受信と同時に発生した本当の編集、外部読み取りの失敗再試行は残す |
| 共有の再試行が正常な本人同期も巻き込む | 未変更の別経路も再照会する | 復旧処理を経路ごとに分離。承認・再ログイン待ちは通知を待ち、未来の再試行期限を尊重 |
| 正常な接続状態でも未送信のTasks完了があり得る | OSの送信待ち判定で変更を落とす | ローカルSQLiteの変更を判定。判定のためにGoogle認証・APIを呼ばない |
| 処理時間切れで後半の連携を実行できなくても成功し得る | カレンダーへの追加などが取り残される | 未実行の連携を未完了として残し、次の処理へ引き継ぐ |
| AIの受領確認失敗が次の解析まで残る | 保存済み結果がサーバーに余分に残る | 起動・復帰・送信待ちの追加・失敗後の再試行で受領だけを送る。空なら認証や送信を始めない |

初期の再配送3ケース、本人端末間の待ち合わせ1ケース、Googleの画面復帰・受信反響4ケース、送信待ち・時間切れ3ケースは、修正前のコードで失敗することも確認した。非同期化した既存の結合検査は、独立した再配送の完了を待ってから受信する形へ変更し、保存内容・権限・暗号の検査は残した。既存の可変名テストの契約参照は、実際に実行される4つの名前へ展開した。

## 通信量と受信の観測

隔離した実Auth／Firestoreへ接続する実SDKに、本文を記録しない計測ラッパーを付けた。以下はアプリが要求した業務SDK操作数であり、TCPパケット数、Firestore内部の再接続回数、提供元の請求額の実測ではない。

| 条件 | 観測結果 |
| --- | --- |
| 復旧対象12件が同時に存在 | 12件すべて到着。同じ完了済み応答の再処理で暗号化本文を再アップロードしない |
| 40件の古い要求の後に新規要求1件 | 増分クエリ1回、取得文書1件。既存40件のメタデータを取り直さない |
| 要求後に送信元が本文を取得 | 追加メタデータクエリ0回で配送を再開 |
| 完了済みの通常読み取りと、永続保存済み本文の再取得 | 余分な業務SDK操作0回 |
| 無変更の前景待機、空のAI受領待ち、承認待ち | 固定タイマーによる業務同期・受領送信を開始しない |
| 受信中の追加編集、通信断、応答紛失、未完了の再試行 | 必要な後続処理を保持し、保存済みの操作や結果を取り落とさない |

受領は端末への永続保存後にだけ送る。別のファイルの受領、保存失敗、古いアカウント、除名、世代変更、改ざんを理由に本文を誤削除しないという既存のCloud回帰も維持した。送信元端末が不在なら復旧を待ち、空データで上書きしない。

AI受領は同じDB・利用者・接続先で同時送信をまとめる。別アカウントは古い送信の完了を待たない。自動再試行には30秒から最大5分のバックオフを置き、既存期限より早く認証を呼び直さない。受領だけでPDF・解析結果を送り直したり、有料解析を新規実行したりしない。

## 残す通信と配備の境界

認証の更新、Firestoreの変更監視、起動・復帰・明示更新、Google側の変更を確認する実操作、未送信・失敗分の再試行は必要な通信として残す。共有と設定は既存の原子的な競合検出単位を維持し、文字単位の差分へ無理に分割しない。通信パケットが常に0になることや、すべてのネットワーク環境で数学的に最小であることを意味しない。

サーバーに残すデータと本文削除の条件は[最小化設計](../security/data-minimization-2026-11-15.md)を維持する。本監査によって保存するユーザー本文や恒久的なログを増やしていない。

稼働中のAPI・Rules・削除ワーカーへの配備と既存データの削除は実行していない。一時配送の既定値は引き続き `EXPO_PUBLIC_SHARING_EPHEMERAL_DELIVERY=0`。全承認端末の準備と実環境の受領・期限切れ復帰の確認後に切り替える。OpenAIの有料実API検査は利用者の指定で保留している。

## 最終検証

2026-11-15、最終のソースで次を確認した。

| `HOUSEWORK_TEST_PLATFORM=android npm test` | 4,396件通過。失敗・キャンセル・スキップ0 |
| 隔離したAuth／Firestoreの全体結合検査 | 173件通過。失敗・キャンセル・スキップ0 |
| `npm run lint`・`npm run typecheck` | 通過 |

全体検査の最初の実行では、既存の検索離脱テストがフォーカス解除関数を1個しか保持せず、新しい同期用フォーカス処理で上書きされる問題が出た。テストを複数の解除関数へ対応させ、検索・下書き・予定を守る期待は維持した。対象検査の成功後、両OS分岐の全体検査を最初から実行し直した結果が上表である。

SQLite・実SDK・Cloud Rulesを通した隔離検査と、シミュレーターでの起動確認を組み合わせている。実Googleアカウントで外部変更を新規作成する検査や、本番の複数端末を長期間オフラインにする検査まで完了したという記録ではない。今回、実機iPhoneは操作せず、新しいシミュレーターも起動していない。
