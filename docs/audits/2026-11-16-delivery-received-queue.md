# 受領済み復旧データの削除待ち解消

古い未受領の復旧要求40件の後ろに受領済み要求があると、削除workerが作成順の先頭32件だけを読むため、受領済みの親・応答・暗号断片が次の約24時間の期限まで残る反例を再現した。共有と本人端末向けの両経路が対象。

2026-11-15 22:36:58〜22:39:17 UTCに案と影響を検討した。受領時刻順と従来の作成時刻順を各32件読み、同じ文書を重複処理しない。削除が進み、取得上限に達した場合だけ次の小さなバッチへ継続する。期限前の未受領データを消さず、空の定期走査や一度の全件走査を増やさない。両キューの読み取り時点が異なっても、受領済みsnapshotを優先する。

単一フィールドのorderByだけを使い、現行の自動indexと照合した。複合indexを追加しない。親を閉じる権限検証と子孫を先に消す順序は維持する。単体5件、関連127件、lint・型検査が成功した。新しいFirestore回帰は旧実装で失敗、新実装の独立実行で成功した。65件の上限付き処理、未受領保持、期限、重複、部分削除失敗と再試行も検査した。

配送17件の連続実行は、既存のslow peer recoveryでtransaction lock timeoutが起き、その後のclearFirestoreも失敗した。差分を戻した旧workerでも同じ7成功・10失敗となることを比較した。期待や必須回帰を緩めず、単独の新回帰成功を全17件の成功へ置き換えない。最終CIのCloud結果は確認後に記録する。

実Cloudでの削除は行っていない。配送の切り替えフラグは0を維持し、未配備workerの新規稼働や既存データの削除を開始していない。
